# The shell is full width, and each page chooses its width

The web app used to put every page in one centred 1,140px column (the project pages in 1,320px), under a navbar sized to match. That suits forms, but not the Issues Board: on a wide screen it showed four or five columns and left the sides empty, and every way of widening only the Board (running it past the column on one side or both) left it out of line with the header and toolbar above it. Linear, Jira and GitHub Projects have no page column at all: the app is full width, and each screen decides how wide its content is. Nimbus now does the same (design "Page widths · full-width shell").

- **The shell is full width.** `AppShell` and `DesktopShell` wrap the page in a fluid container with one gutter on each side, and the top or bottom navbar spans the same width, so every page's left and right edges line up with it.
- **Work surfaces fill the width:** the Projects table and the project pages (Overview, the Issues views, project Settings). Wide screens add columns, not width: the Projects table gains columns and the Board fits more Statuses. Spare space goes to a panel (an Issue peek, for instance), never to stretched cards.
- **Reading and form pages cap their column, not the page:** a form is at most 720px, centred in the space it is given but never more than 200px from what it belongs to (the Settings list), so on a very wide screen it doesn't drift off on its own; an Issue's page is full width like the rest, so its breadcrumb stays where the project pages put theirs: its text from the left gutter and its details at the right gutter (340px to 460px, growing with the screen), the text filling the space between so no gap opens on a wide screen; a table inside Settings (Roles & access, a Role, the Audit log) takes the whole space. A page sets its own width; the shell never does.
- **Settings in a browser is a list and a page**, like the Desktop app's Settings overlay: the same list of Settings pages (`SettingsNav`) on the left, the open page beside it (`SettingsLayout`), and no overview page or breadcrumbs (`/settings` opens Profile). Adding a Settings page means adding it to `settingsGroups` once; both places show it.

Going back to a centred column would mean giving every work surface its own width again and re-aligning the navbar, and the Settings list would lose the browser half of its sharing.
