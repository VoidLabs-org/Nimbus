# issues

Owns **Issues**, their **Statuses** and (later) their history views. So far it implements creating an Issue, opening it by key, finding a project's Issues, editing an Issue (fields, Assignee and history) and moving it between Statuses; deleting, Status management and permissions are not implemented yet. Feature spec #51, tickets #53, #54, #55 and #56. Terms are in [GLOSSARY.md](../../GLOSSARY.md).

## Public interface

`Issues` (implemented by `IssueService`): `changeStatus(actor, issueKey, statusId)` moves an Issue to a Status of its project and returns that `ProjectStatus`; `statuses(projectId)` lists a project's Statuses with their category and order (`ProjectStatus(id, name, category, position)`) and does not check who asks. `changeStatus` is the single move operation: the endpoint calls the same code, so transition rules go in one place. Refusals are thrown as the module's own exceptions (unchecked), which the endpoint maps to `400`, `404` and `409`. Everything under `issues.internal` is private, apart from the events below. The module uses only the public APIs of `projects` (`findByKey`, `isMember`, and the `archived` flag of `ProjectSummary`) and `identity` (`Users.findAllById`, for the Reporter's and Assignee's names and pictures).

## Events published

`IssueChanged(projectId, issueKey, changedFields)` is published once per edit that changed something, in the same transaction. `changedFields` lists the fields that really changed, among `title`, `description`, `type`, `priority`, `assignee` and `status`. Edits that change nothing (the same values again), and refused edits (validation, stale version, not a Member, Archived project), publish nothing. Consumers should handle it after commit.

`IssueCreated(projectId, issueKey)` is published once, in the transaction that inserts the Issue. The key is uppercase, like `NIM-12`. Reads and refused creates (validation, not a Member, Archived project) publish nothing. Consumers should handle it after commit.

## Rules

- **Interim check.** `IssueAccess.require(actor, projectId, action)` is the single decision for every action: it allows any Member and gives "not found" to everyone else. The permission integration (#48) replaces its body with `access`'s check and declares the Permissions in the catalog, without touching callers.
- **Issue key.** The Project key (uppercase), a dash and the number: `NIM-12`. It matches in any case on lookup. Only ASCII letters and digits are accepted, and a number is 1 to 9 digits with no leading zero; anything else matches nothing, so it is "not found", not an error.
- **Numbers** count up per project from 1. `issue_counters` holds the last number used per project; creating an Issue increments it with a single `UPDATE ... RETURNING`, which locks the row until the transaction ends, so concurrent creates queue up and get distinct numbers. Numbers only go up, so one is never given again, and a create that fails after taking a number rolls the increment back with everything else.
- **Statuses.** Each project has its own ordered Statuses (`issue_statuses`). Nothing listens to `ProjectCreated`: the first create in a project that has none makes To do (category `TODO`), In progress (`IN_PROGRESS`) and Done (`DONE`), in that order, while holding the counter row's lock, so they are made once even under concurrent requests, and projects that existed before Issues do the same. A new Issue starts in the first Status, in order, whose category is `TODO`.
- **Fields.** Type is `Story`, `Bug` or `Chore`. Title: surrounding whitespace removed, then 1 to 255 characters, no control characters. Description: optional Markdown of at most 50,000 characters, stored as typed (the web app sanitises it when rendering). Priority is `Urgent`, `High`, `Medium` or `Low`, `Medium` when omitted. Invalid fields give `400` with `errors` keyed by field, like `projects`.
- **Reporter** is the creating User and never changes. **Assignee** is optional and must be a Member of the project: otherwise `400` with `errors.assigneeId`.
- **Archived projects** refuse new Issues and every edit with `409`; reading, including history, still works. `issues` asks `projects` before each write.
- **Editing.** Title, description, type and priority change with `PATCH`; only the fields sent change, and `null` or absent means unchanged. An empty description clears it. Validation is the same as creating. The Assignee is set with `PUT .../assignee`, where `null` unassigns, and must be a Member (`400` with `errors.userId`). The Reporter never changes (a `reporterId` in the body is ignored). Sending a field's current value changes nothing: no history, no event, no new `updatedAt`.
- **Version.** `version` guards title and description. It is required when the title or description sent really differs from the current one (`400` with `errors.version` if missing) and must equal the Issue's current one, otherwise `409` with code `issue_changed`; sending the current text again needs no version and never conflicts. Only a changed title or description raises it, so quick changes (type, priority, Assignee) need no version and never make someone's open text edit stale. The Issue row is locked (`SELECT ... FOR UPDATE`) while it is compared and changed, so of two edits with the same version one wins and the other gets `409`.
- **History.** Creating writes a `created` entry (actor = the Reporter, no before or after). Each changed field writes one entry with the actor and time: title, type and priority keep the old and new text, and a description entry keeps neither (it is up to 50,000 characters, so the entry only says it changed); an Assignee change keeps the old and new User ids, which `GET .../history` returns as display names ("Unknown user" if the User is gone). Entries from one edit share a time and come back in a fixed order (by field name, descending). History is returned newest first and is never edited.
- **Moving.** `PUT .../status` takes any Status of the Issue's project, in any direction; no version is needed and it never raises one. A Status of another project, an unknown one or a missing `statusId` is `400` with `errors.statusId`. Moving to the Status the Issue is already in changes nothing. A move writes a `status` history entry holding the old and new Status names as they were then, and `IssueChanged` lists `status`. It takes the same Issue row lock as other edits, and an Archived project refuses it with `409`.
- Unknown projects, unknown Issues and projects the User is not a Member of all give `404`. Missing or invalid access tokens give `401`; an unverified email gets the identity gate's `403`.

## REST endpoints

Contract: [openapi.yaml](openapi.yaml).

| Endpoint                              | Behavior                                                                                                                                                                    |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/projects/{key}/issues`     | `{type, title, description?, priority?, assigneeId?}` → `201` with the Issue. `400` field errors, `404`, `409` (Archived).                                                  |
| `GET /api/projects/{key}/issues`      | One page of the project's Issues, filtered and sorted (below): `200` with `{items, total, page, size}`. `400` for invalid parameters (`errors` keyed by parameter), `404`.  |
| `GET /api/issues/{issueKey}`          | The Issue for a Member, with the key in any case: `200`; otherwise `404`.                                                                                                   |
| `PATCH /api/issues/{issueKey}`        | `{title?, description?, type?, priority?, version?}` → `200` with the Issue. `400` field errors, `404`, `409` (Archived, or stale `version` with code `issue_changed`).     |
| `PUT /api/issues/{issueKey}/assignee` | `{userId                                                                                                                                                                    | null}`→`200`with the Issue.`400`for a non-Member,`404`, `409` (Archived). |
| `PUT /api/issues/{issueKey}/status`   | `{statusId}` → `200` with the Issue. `400` for a Status of another project, `404`, `409` (Archived).                                                                        |
| `GET /api/projects/{key}/statuses`    | `200` with the project's Statuses in order `{id, name, category, position}` (empty until its first Issue); `404`.                                                           |
| `GET /api/issues/{issueKey}/history`  | `200` with entries `{id, actor, at, field, before, after}`, newest first (`field` is `created`, `title`, `description`, `type`, `priority`, `assignee` or `status`); `404`. |

**Finding Issues.** Parameters, all optional, combine with AND; an empty result is a normal `200` with `total` 0.

- `status`: a Status name, ignoring case. `category`: `TODO`, `IN_PROGRESS` or `DONE`. `type` and `priority`: as on create.
- `assignee`: a User id, `me` (the caller) or `none` (unassigned).
- `q`: split on whitespace; every word must appear in the title, in any case. `%`, `_` and `\` in a word are plain text. At most 10 words and 200 characters, otherwise `400`.
- `sort`: `updated` (default, most recently updated first), `created` (newest first) or `priority` (Urgent first, then most recently updated). Ties end with the highest number first, so paging never repeats or skips an Issue.
- `page` (from 0, default 0) and `size` (1 to 100, default 50). A page beyond the last is empty. `total` counts the matches across all pages.

An Issue is `{id, key, number, type, title, description, priority, status: {id, name, category}, reporter: {id, displayName, avatarUrl}, assignee: {…} | null, createdAt, updatedAt, version}`. `version` starts at 0. Times are in microseconds, as the database keeps them.

## Tables

Migration `V25__issues.sql`.

| Table            | Columns and constraints                                                                                                                                                                  |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `issue_statuses` | `id`, `project_id` → `projects`, `name` (unique per project ignoring case), `category` (`TODO`, `IN_PROGRESS`, `DONE`), `position`.                                                      |
| `issue_counters` | `project_id` primary key → `projects`, `last_number`.                                                                                                                                    |
| `issues`         | `id`, `project_id`, `number` (unique with project), `type`, `title`, `description`, `priority`, `status_id` → `issue_statuses`, `reporter_id`, nullable `assignee_id`, times, `version`. |
| `issue_history`  | `id`, `issue_id` → `issues` (deleted with it), nullable `actor_id` (null is the system), `at`, `field`, nullable `before_value` and `after_value`. Never edited.                         |

## Web app

The project page has a **Create Issue** button (hidden for an Archived project) that opens a form above the project details: Issue type, Title, Markdown Description, Priority and Assignee. Until the project's Members can be listed, the Assignee choices are Unassigned and the User themself. Field errors appear on their fields; success shows a toast and opens `/issues/:issueKey`. A create that finishes after the User has left the page shows a toast and does not navigate.

`/projects/:key/issues` lists the project's Issues: quick filters (Everyone, Assigned to me, Unassigned), a title search (applied once typing pauses), Status category, Issue type and Priority selects, a sort choice, paging at 50 a page and **Create Issue** (hidden for an Archived project). The filters live in the address, so a filtered list can be shared and survives a reload; values it does not recognise are ignored. Each row shows the title, key, type, priority, Status and Assignee, and opens `/issues/:issueKey`. The project page links to it with **View Issues**. There is no Status filter in the web app until the project's Statuses can be listed; the API takes `status` already.

`/issues/:issueKey` shows the key, type, title, description, Status, priority, Reporter, Assignee and the history, newest first. **Edit title** and **Edit description** open an inline editor with Save and Cancel; they send the `version` the page was opened at. If the Issue's version changes while the editor is open (a refresh saw it), or the save is refused as stale, an alert says "This Issue changed since you opened it", Save is disabled and **Load the latest** discards the edit and reloads, but the typed text stays on screen until then. Status, Issue type, priority and Assignee are selects that save as soon as one is chosen; the Status select lists the project's Statuses in order, with the current Status's category beside it. Until the project's Members can be listed, the Assignee choices are Unassigned, the User themself and the current Assignee. The description is rendered with `react-markdown` and `remark-gfm` (checklists, tables): raw HTML is never rendered (a pasted `<script>` shows as text) and unsafe link addresses such as `javascript:` are dropped. Unknown keys, and Issues of projects the User is not in, show "Issue not found."

## Verification

`CreateIssueTests` (HTTP, against disposable PostgreSQL) covers creating, defaults, numbering per project, concurrent creates (distinct numbers, one shared To do Status), lazy Statuses, validation, Assignee rules, `404` for non-Members and unknown keys, `401`, the Archived refusal and the `created` history entry. The last two checks read the tables directly. `FindIssuesTests` covers each filter and their combinations, title words (including wildcard characters), each sort, paging with the total, invalid parameters, `404` and `401`; it sets Statuses and update times in the tables directly. `IssueCreatedEventTests` is a Spring Modulith module test of the event. `EditIssueTests` covers each change, the version rules (including two concurrent edits at the same version), validation, non-Member Assignees, the Reporter, history entries and their order, the Archived refusal, `404` and `401`. `IssueChangedEventTests` is the module test of `IssueChanged`. `IssuesPage.test.tsx` checks the list, filters read from and sent to the API, paging and Create Issue. `IssuePage.test.tsx` checks the page, the Markdown rendering, the not-found screen, saving a title with its version, the stale-version message, the quick changes and the history order. `MoveIssueTests` covers the Statuses list, moves in any direction without a version, a Status of another project or a missing one, history, the Archived refusal, `404`, `401` and that `Issues.changeStatus` and the endpoint behave the same. `IssueChangedEventTests` also checks that a move publishes `status`. `ModularityTests` checks the module boundaries.
