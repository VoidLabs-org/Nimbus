# projects

Owns **Projects** and their **Members**. So far it implements creating a project, listing the projects a User is a Member of, and opening one; editing, archiving and Member management are not implemented yet. Feature spec #36, tickets #38 and #39. Terms are in [GLOSSARY.md](../../GLOSSARY.md).

## Public interface

`Projects` offers `findById(UUID)`, `findByKey(String)` (case-insensitive), `isMember(projectId, userId)`, and `memberProjects(userId)`: the User's active projects, in the list's order (the issues module uses it for the Projects table's Issue totals). Lookups return an optional `ProjectSummary(id, key, name, archived)`; an unknown project gives an empty result, and missing membership gives false. These are internal application lookups, not authorization checks. A consuming module must authorize its caller and check `archived` before writing into a project. Everything under `projects.internal` is private.

## Events published

`ProjectCreated(projectId, key, creatingUserId)` is published once in the transaction that inserts the project and its first Member. The key is uppercase. Reads, rejected input and conflicting creates publish nothing. Consumers should handle it after commit. `access` does not listen to it: later RBAC integration calls `access` from `projects`, as required by [ADR 0002](../adr/0002-per-project-roles-and-access-as-a-foundation.md).

## Rules

- The existing identity gate requires a signed-in User with a verified email. An Unverified User gets `403` with `code: email_unverified` before a project endpoint runs.
- Any verified User can create a project and becomes its first Member in the same transaction. Only Members can open it. Unknown and non-Member projects both give `404 Project not found`.
- The list holds only the projects the User is a Member of, and only active ones: an Archived project is left out. It is sorted by lower-cased name (Java's `toLowerCase(Locale.ROOT)`, as the Roles are), then by key, so projects with the same name always come in the same order. The sorting is done in code, not by the database, so the order is the same on every database: a collation would skip spaces and punctuation, and its `lower()` differs from Java's. There is no paging, and a User with no projects gets an empty list, not an error.
- `ProjectService.requireCanChange(actor, projectId)` is the single internal change decision for subsequent tickets: any Member may change the project for now. Future RBAC integration replaces this decision. Permission declarations already exist, but this slice does not enforce scoped Grants or give project Roles.
- Project key: 2–10 ASCII letters/digits, starting with a letter, accepted in either case and stored uppercase. Whitespace is not accepted. Keys are unique across all projects, including Archived projects, and have no change or deletion operation. The database constraint also resolves concurrent creation attempts: one succeeds, the others get `409` without acquiring membership.
- Name: surrounding whitespace is stripped; 1–100 Unicode code points, no ISO control characters. Names need not be unique.
- Description: nullable plain text, at most 1000 Unicode code points. Like the name it is cleaned at both ends (whitespace, Unicode spaces, invisible format characters), so every client gets the same result; one with nothing left, an empty string included, is none (`null`). Line breaks and tabs inside it are kept; other control characters are a field error. Omitted and null descriptions remain null.
- Fields are checked with Bean Validation on the request (`400` with `errors` keyed by field, the same shape as `access` and `identity`). The name is cleaned at both ends before it is checked: whitespace (a pasted trailing newline too), Unicode spaces such as a non-breaking space, and invisible format characters such as a zero-width space. A name of only those is empty and rejected. Created and read times are in microseconds, as the database keeps them, so the time in the `201` is the one a later read returns.
- Creation and membership timestamps are stored together. New projects are not archived; the archived state is exposed now for future consumers.

## REST endpoints

Contract: [openapi.yaml](openapi.yaml).

| Endpoint                  | Behavior                                                                                                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/projects`       | The User's active projects, sorted by lower-cased name, then key: `200` with an array of projects, empty when there are none.                                                |
| `POST /api/projects`      | `{key, name, description?}` → `201` with the project. `400` with `errors` keyed by field for invalid input; `409` with `errors.key` for a taken key.                         |
| `GET /api/projects/{key}` | The project for a Member, matched case-insensitively: `200`; otherwise `404`. A key that is not 2–10 ASCII letters or digits matches nothing (so `ſam` does not open `SAM`). |

Each project is `{id, key, name, description, archived, createdAt, createdBy, memberCount, members}`, the same wherever it appears, in the list too. `createdBy` is the creating User as `{id, displayName, avatarUrl}`, or `null` when they are no longer known. `memberCount` counts the Members; `members` names the first five as the same `{id, displayName, avatarUrl}`, earliest added first (a Member no longer known is counted but not named). One query reads the Members of every listed project and one lookup through identity's `Users` finds everyone named, however long the list. `createdAt` is an ISO timestamp. Missing or invalid access tokens get `401`; unverified email gets the identity gate's `403`.

## Tables

Migration `V14__projects.sql` adds the tables below. It was numbered while `V15` was already on `main`, so the API runs Flyway with `spring.flyway.out-of-order=true`: a database that has applied `V15` but not `V14` applies `V14` on its next start instead of refusing to boot.

| Table             | Columns and constraints                                                                                                                                                                                         |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `projects`        | `id` UUID primary key, `key` unique and uppercase ASCII format checked, `name`, nullable `description`, nullable `archived_at`, `created_at`, nullable `created_by` → `users` (null when that User is deleted). |
| `project_members` | `project_id` → `projects`, `user_id` → `users`, `added_at`; primary key `(project_id, user_id)` and index on `user_id`. No Role data.                                                                           |

`V28__projects_created_by.sql` adds `created_by`, set when a project is created. Existing projects take their first Member, who is the creator: creating a project adds its creator as the first Member in the same transaction. `V29__projects_created_by_set_null.sql` makes the reference `ON DELETE SET NULL`, as for the other references to a User who acted, so deleting a User leaves their projects with no creator (`createdBy` null) instead of being refused. It is a separate migration because V28 had already been applied to the shared development database.

## Web app

The shared navbar has a **Projects** link in horizontal, vertical and narrow layouts, active throughout `/projects`. `/projects` shows the User's projects as a full-width table, by name (a work surface, see [ADR 0011](../adr/0011-the-shell-is-full-width-and-pages-choose-their-width.md)): the key, the name with the key in a round badge (one of three colours, picked from the key) and one line of the description, who created it, the open Issues (not in a Done Status), Progress (Done out of all, as a bar and a percentage), the Members (up to five overlapping pictures and "+N" for the rest, their names as the tooltip), and when an Issue last changed (the project's creation when none has), each row opening `/projects/:key`. The Issue figures come from `GET /api/issues/stats`, one request for all the projects. A search box (`/` focuses it) narrows the table by name, key or description, with the number of projects beside it. On a phone only the project and its open Issues show. A User with no projects sees "No projects to show yet" in place of the list (the list is of active projects, so it says nothing about membership). **New project** in the page header appears once the list has loaded, as **New Role** does, so a failed first load, which replaces the whole page with the error screen, can never discard an open form. It opens the **New project** window (the Role windows' frame), with Name focused; the window checks the name (not empty), the key (2 to 10 letters or digits, starting with a letter) and the description (at most 1000 characters) without asking the server, when the User leaves a field and again as they type once it shows an error, and on submit; a key one of the User's own projects already has is said at once (from the list already loaded), and only a key taken by a project they aren't a Member of needs the server. The key field shows the Issue keys it will give (`NW-1`, `NW-2`…), its error in place of its hint, and the description its length out of 1000. Cancel or ✕ closes the window, drops what was typed and puts focus back on **New project**. A first load shows a delayed skeleton, a returning visit shows the cached list and refreshes it, and a failed refresh is visible with a retry action. A key is suggested from the name (word initials, or the first three characters for one word), up to ten characters; no key is suggested when it would be shorter than two. The key follows the name while it is empty or still the suggestion, and stays as typed once the User changes it. The form sends the description as typed; the server cleans it. A create that finishes after the User has closed the window or left the page does not navigate; a success still shows its toast, and a failure shows an error toast, since the form is gone. Invalid or taken keys and other field errors appear on their fields. Success opens `/projects/:key` and shows a toast.

Every page of a project shares one layout (`ProjectLayout`, design "Project page layouts", A): the breadcrumb (`Projects › <name> › <tab>`, the name linking to Overview), a header with the key badge, the name, the key (and **Archived**) and **Create Issue** on the right (hidden for an Archived project or a User who may not create Issues), and under it left-aligned underline tabs: **Overview** (`/projects/:key/overview`), **Issues** (`/projects/:key/issues`) and, for a User who may manage Statuses, **Settings** (`/projects/:key/settings/statuses`). The layout is drawn once, at one width, around the open tab's page, so the tabs stay in the same place on every tab; the open tab is marked by colour and an underline, not a bolder weight, so it doesn't nudge the others. `/projects/:key` opens Issues, keeping its query string (`?view=board`). Overview shows the plain-text description, with a fallback when none is set. Unknown and non-Member keys show the same **Project not found** screen in place of the whole layout. The pages reuse the app shell, breadcrumbs, Panel, skeletons, toasts and error screens in all four themes. Data uses the session-scoped TanStack Query cache (`queryKeys.projects` for the list, `queryKeys.project(key)` for one; `useProjectCreated` stores the created project, so opening it shows it at once and then refreshes it, and refreshes the list, which has a new project, and the Issue totals (`queryKeys.projectIssueStats`), which have none for it yet, as the Roles are refreshed after a change; creating, moving or deleting an Issue refreshes the totals too). A project the list already holds shows at once when opened from it, from the list's copy and without a skeleton, and is then refreshed; the address is matched to the list as the server matches it, ASCII letters only, so `ſap` does not show `SAP`. Both pages load, refresh and fail as described above. There are no editing controls in this slice.

## Verification

HTTP tests register and verify Users through identity's endpoints and exercise creation, validation, membership isolation and conflicts against disposable PostgreSQL. The list has its own tests: only the User's own projects, sorted by lower-cased name (including a case where a database collation would order the same names differently), the key as tie-break, Archived projects left out (until #41 there is no archive endpoint, so that test sets the state directly and checks the API's answer), the same shape as opening a project, who created each project, and the Member count with the first five Members, earliest first, and the sign-in rules. `ProjectStatsTests` (in issues) covers `GET /api/issues/stats`: each project's total and Done count in the list's order, a deletion counting as the latest change, only the User's own active projects, an empty list and the sign-in rule. A Spring Modulith module test checks the event and public lookups. The API client is tested through its fetch boundary. The Projects page and the project page have page tests with the API client's calls stubbed (`ProjectsPage.test.tsx`, `ProjectPage.test.tsx`): the list, the empty state, the failed first load and failed refresh, each project's creator, open Issues, Progress and last change, the search, "+ New project" waiting for the list, focus going to Name and back, the key suggestion, field errors, the list refreshing after a create, an error toast when a create fails after the User has left, and a project the list holds opening at once. The feature spec #36 planned to check pages by hand only; the review of #39 asked for these. The Description rule is checked without a server in `CreateProjectTests`. All tests avoid the shared development database.
