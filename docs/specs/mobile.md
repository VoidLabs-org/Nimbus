# mobile

The Mobile app (`apps/mobile`): Nimbus for Android and iOS, built with React Native, Expo and Expo Router ([ADR 0009](../adr/0009-the-mobile-app-is-react-native-with-expo.md)). It is not a backend module, so there is no public interface or events here; this describes how it works now. Its features are planned in #198; this file grows with each ticket. How to run it: [apps/mobile/README.md](../../apps/mobile/README.md).

## What it holds now

Sign in with email and password, with Two-step verification, Create an account with email verification, Forgot password, staying signed in between launches, Home, and Sign out. Inbox is a placeholder until #208; Settings shows who is signed in and Sign out. Projects and Issues are on the web for now.

## Talking to the API

- **Address.** `EXPO_PUBLIC_NIMBUS_API_URL`, default `http://localhost:8080`. The app calls the API directly, with no proxy. In development an Android emulator or a phone on USB reaches the computer's `localhost` through `adb reverse` (README).
- **Credentials** ([ADR 0010](../adr/0010-the-mobile-app-gets-its-tokens-in-the-body.md)). Every request sends `X-Nimbus-Client: mobile`, so the API answers the refresh token in the body (`refreshToken`) and sets no cookie (see [identity.md](identity.md)). The refresh token is kept in the phone's secure storage (`expo-secure-store`: the iOS Keychain or the Android Keystore), under `nimbus.refreshToken`, and read from there once per launch (the pending Two-step sign-in and remembered devices are kept there too, see Signing in); while the app runs, its copy in memory is the one used. A rotated token is taken in memory first and then stored, so a storage write that fails leaves this launch signed in and only the next one asks to sign in. The access token lives only in memory. One refresh runs at a time, as on the web, because a used refresh token coming back ends the Session; signing in, signing out and forgetting wait for a refresh under way, and a refresh that started before one of them throws its answer away.
- **User-Agent** (`nimbusUserAgent`). `Nimbus/<version> (<phone>)`, with the version from `app.json`: `(Android 15)`, `(iPhone; iOS 18.1)` or `(iPad; iPadOS 18.1)`. The Sessions list names the Session "Nimbus for Android", "Nimbus for iPhone" or "Nimbus for iPad" (`DeviceLabels`).
- **Shared code.** Errors, the problem-detail parsing and the messages come from `@repo/api`, the User type from its generated contract types, and the theme from `@repo/tokens`. Server data goes through TanStack Query, as on the web ([ADR 0003](../adr/0003-tanstack-query-for-server-data.md)).

## The Session

`SessionProvider` (`src/session/session.tsx`) knows where the app stands, and the root layout shows only the screens that state allows (`Stack.Protected`, each redirecting to the state's own screen):

| State        | When                                                                             | Screen                                                                                                        |
| ------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| starting     | Launch: reading storage and renewing a stored Session                            | The splash screen stays up                                                                                    |
| signed out   | Nothing stored, after Sign out, or after "Sign in again"                         | Welcome on the first launch only (`nimbus.welcomed`), then Sign in; Create an account and Forgot password     |
| signed in    | A right password, a registration, or a stored Session renewed                    | The tabs: Home, Inbox, Settings. An Unverified User sees only the verify-email screen                         |
| expired      | The server refused the refresh token (`401`), at launch or while the app is open | "Your session expired." Sign in again returns to the screen the User was on                                   |
| offline      | Renewing at launch couldn't reach the server                                     | "You're offline." with Try again; still signed in                                                             |
| server error | Renewing at launch got any other failure (a `5xx`, a `429`)                      | "Something went wrong on our side" with Try again, and Sign out, which forgets the Session on this phone only |

- **Signing in.** Web's messages: "Invalid email or password." for a `401`, the wait for a `429`, field errors under their fields. Without a connection: "Can't reach Nimbus."
- **Two-step sign-in.** For a User with Two-step verification a right password answers a `pendingToken` (ADR 0010), kept in memory and in secure storage (`nimbus.pendingSignIn`) until the code step ends (a right code, a timeout, going back to Sign in, or the next launch), and the app opens "Two-step verification": the six boxes for the Sign-in code, or "Use a recovery code" for the Recovery code field, and "Remember this device for 30 days". Verify sends `{pendingToken, code or recoveryCode, rememberBrowser}` to `/api/auth/two-step`. Web's messages: the tries left after a wrong code (a Recovery code's own wording), the hourly lock's wait counting down with Verify off. A pending sign-in that timed out or ended (`sign_in_expired`) goes back to Sign in with "Your sign-in timed out. Sign in again."
- **Remembered devices.** With the box ticked, the right code's answer carries a `rememberedToken`, kept per User in secure storage (`nimbus.rememberedDevices`, one JSON entry of `{userId, token}` by the lower-cased email they signed in with; remembering again replaces the User's entry under an earlier email, and changes to the entry run one after another). Signing in with that email sends it as `rememberedToken`, and the server skips the code for 30 days. Signing out keeps it, as on the web; another User signing in on the phone is still asked for their code. If the server asks for a code anyway, the token is no longer known (expired, a password change, Remove) and is forgotten.
- **Creating an account** takes a name, email and password, with the web's checks before sending (`displayNameError`, `emailError`, `passwordError` from `@repo/api`) and its messages after: the server's text under Email for a `409`, field errors under their fields, the wait for a `429`. The new User is signed in at once, as an Unverified User.
- **Verifying the email.** An Unverified User (`emailVerified` false), whether just registered, signed in or reopening the app, sees only "Check your email": six boxes for the Verification code (one see-through field over them, so the keyboard's suggested code and a long-press paste work), sent by the last digit. A right code renews the Session at once, so the access token says "verified", and the app opens. Web's messages for a wrong code (with the tries left), a gone one and a `429`. Resend mails a new code, then counts down 60 seconds, or the server's `Retry-After`; a `409` there (verified on another device) reads the User again, which opens the app. Sign out and "Use a different email" end the Session; without a connection the User stays and is told so.
- **Forgot password**, from "Forgot password?" on Sign in: an email, then the Reset code and the new password on one screen, as on the web, with its messages for a wrong code, an expired one (only "Send a new code" is left), a `429` on sending (Send code counts the wait down) and on resetting (Reset password is off while the wait counts down). A right code goes back to Sign in with the email filled in and a toast: "Password updated. You were signed out on other devices." A User with Two-step verification is asked for a Sign-in code too, or a Recovery code, once the Reset code is right (`two_step_required`), as on the web; the Reset code and the password stay as typed, and a wrong second code gets web's messages.
- **While open.** A request answered `401` renews the Session once and tries again. When renewing is refused too, the stored token is deleted, the cached server data is dropped and the app shows "Your session expired" (once, however many requests were waiting). The User from signing in or the launch counts as fresh for a minute; after that, coming back to the app (TanStack Query's `focusManager`, fed by `AppState`) reads stale data again.
- **Signing out** (Settings, confirmed in a bottom sheet) ends the Session on the server with the stored token, then deletes it and drops the cached data. If the server can't be reached the User stays signed in and the sheet says so, as on the web. If the server fails (a `5xx`), the sheet also offers **Sign out on this phone only**, which forgets the Session here; it stays in the Sessions list until it expires or is signed out from another device.

## Look

Paper in light mode and Ink in dark, following the phone until Appearance (#209); Fog and Slate are web only. Poppins is bundled (`@expo-google-fonts/poppins`, loaded with `useFonts`); if it fails to load, the system font takes its place. The brand bars show on the first-launch Welcome screen and the status screens (design option 1d); Sign in is just the logo and the form. Confirmations are bottom sheets. The app icon and splash use `apps/web/public/nimbus-icon-*.png`; Android's adaptive icon still needs its own artwork with the safe-zone padding before a store release.

## Tests

`pnpm --filter mobile test`: Jest (`jest-expo`) with React Native Testing Library. Each test renders the real `src/app` routes with Expo Router's test renderer (`renderApp` in `src/test-support.ts`), with `fetch` answered by a fake API that records every request, and secure storage kept in memory (`jest.setup.ts`). Tests follow what a User does and check what is on screen, what was sent and what is stored.
