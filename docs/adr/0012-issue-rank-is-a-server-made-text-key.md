# An Issue's Rank is a text key the server makes from its neighbours

Each project keeps one manual order of its Issues (their **Rank**), which the Board, Swimlanes and List show and which a later Backlog and Sprints will reuse. It is stored as a short text key per Issue (fractional indexing, base 62) that sorts with a plain `ORDER BY`. A move sends only the Issues above and below where it was dropped (`after`, `before`); the server makes a key between theirs and writes that one row. Clients never see or send keys, so the scheme can change later without touching the API or the apps.

- **Considered options.** Integers with gaps (1000, 2000, …) run out of gaps in busy columns and then need a renumbering under a lock. A linked list (each Issue points to the next) makes a filtered, paged column a recursive query. Floats lose precision after about 50 drops in the same gap. Jira's LexoRank is the same idea as ours plus buckets and a background job that renumbers gradually while people keep dragging; that machinery only pays off when one project is too big to renumber in a single transaction.
- **Keys grow, so they get renumbered.** Each drop into the same shrinking gap adds about a character every 5 or 6 drops. When a key passes about 50 characters, the server rewrites that project's keys evenly in one transaction, under the project's `issue_counters` lock (the one creating an Issue takes), which also keeps two drops from getting the same key. Switch to LexoRank-style gradual renumbering only if a single project grows so large (hundreds of thousands of Issues) that this rewrite blocks people.
- **The column is `COLLATE "C"`**, so keys sort byte by byte. The database's default, language-aware collation would order base 62 keys wrongly, and nothing would fail loudly.
- **Indexed by `(status_id, rank)`**, so each column reads its first page in order straight from the index however big the project gets.
