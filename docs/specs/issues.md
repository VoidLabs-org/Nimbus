# issues

Owns **Issues**, their **Statuses** and (later) their history views. So far it implements creating an Issue, opening it by key, finding a project's Issues, editing an Issue (fields, Assignee and history), moving it between Statuses, deleting it, managing a project's Statuses, each Issue's Rank, and the Permissions that guard them. Feature spec #51, tickets #53, #54, #55, #56, #57, #58 and #59; Rank: feature spec #232, tickets #233, #234, #235 and #236. Terms are in [GLOSSARY.md](../../GLOSSARY.md).

## Public interface

`Issues` (implemented by `IssueService`): `changeStatus(actor, issueKey, statusId)` moves an Issue to a Status of its project and returns that `ProjectStatus`; `statuses(actor, projectId)` lists a project's Statuses with their category and order (`ProjectStatus(id, name, category, position)`) for a Member; a non-Member gets "not found". `changeStatus` is the single move operation: the endpoint calls the same code, so transition rules go in one place. Refusals are thrown as the module's own exceptions (unchecked), which the endpoint maps to `400`, `404` and `409`. Everything under `issues.internal` is private, apart from the events below. The module uses only the public APIs of `projects` (`findByKey`, `isMember`, `memberProjects` for the per-project totals, and the `archived` flag of `ProjectSummary`) and `identity` (`Users.findAllById`, for the Reporter's and Assignee's names and pictures).

## Events published

`IssueChanged(projectId, issueKey, actorId, title, reporterId, assigneeId, changes, at)` is published once per edit that changed something, in the same transaction. `title`, `reporterId` and `assigneeId` (`null` when unassigned) are the Issue after the change; `actorId` made it and `at` is when. `changes` has one `Change(field, before, after, beforeCategory, afterCategory)` per field that really changed, among `title`, `description`, `type`, `priority`, `assignee` and `status`; `before` and `after` are the values (the Status name for `status`, User ids for `assignee`, `null` for nobody; the two categories, `TODO`, `IN_PROGRESS` or `DONE`, are set only for `status` and are `null` otherwise). A `description` change is only a flag with both values `null`, as its text is never carried. Edits that change nothing (the same values again), and refused edits (validation, stale version, not a Member, Archived project), publish nothing. Consumers should handle it after commit.

`IssueCreated(projectId, issueKey, actorId, title, reporterId, assigneeId)` is published once, in the transaction that inserts the Issue. The key is uppercase, like `NIM-12`. `actorId` is who created it (the Reporter too); `assigneeId` is null when unassigned; `title` is the title at creation. Reads and refused creates (validation, not a Member, Archived project) publish nothing. Consumers should handle it after commit.

`IssueDeleted(projectId, projectKey, projectName, issueKey, actorId, title, reporterId, assigneeId, at)` is published once, in the transaction that deletes an Issue. `actorId` deleted it at `at` (the `deleted_at` of its `issue_deletions` record); `title`, `reporterId` and `assigneeId` (`null` when unassigned) are the Issue as it was. Refused deletes (not a Member, unknown or already deleted key, Archived project) publish nothing. Consumers should handle it after commit.

## Rules

- **Permissions.** `IssuePermissions` declares `issues:issue:create` (PROJECT), `issues:issue:edit` (OWN, PROJECT), `issues:issue:delete` (OWN, PROJECT) and `issues:status:manage` (PROJECT) with these defaults: Project admin has all four at PROJECT; Developer has create and edit at PROJECT and delete at OWN; Viewer has none. `IssueAccess.require(actor, projectId, action)` is the single decision for every action. A User who is not a Member and lacks `projects:project:view` with Scope All gets "not found"; a Member (or such a holder) without the Permission gets `403`. Viewing needs no Permission. It returns the Scope; for OWN the service then calls `requireOwn` once it has the Issue row: edit is for the Reporter or the Assignee, delete for the Reporter only (`403` otherwise). A Platform admin holds every Permission at ALL, so acts in every project.
- **Issue key.** The Project key (uppercase), a dash and the number: `NIM-12`. It matches in any case on lookup. Only ASCII letters and digits are accepted, and a number is 1 to 9 digits with no leading zero; anything else matches nothing, so it is "not found", not an error.
- **Numbers** count up per project from 1. `issue_counters` holds the last number used per project; creating an Issue increments it with a single `UPDATE ... RETURNING`, which locks the row until the transaction ends, so concurrent creates queue up and get distinct numbers. Numbers only go up, so one is never given again, and a create that fails after taking a number rolls the increment back with everything else.
- **Statuses.** Each project has its own ordered Statuses (`issue_statuses`). Nothing listens to `ProjectCreated`: the first create in a project that has none makes To do (category `TODO`), In progress (`IN_PROGRESS`) and Done (`DONE`), in that order, while holding the counter row's lock, so they are made once even under concurrent requests, and projects that existed before Issues do the same. A new Issue starts in the project's default Status (see below).
- **Managing Statuses.** Holders of `issues:status:manage` (Project admins by default) may add, rename, reorder, re-categorise and delete a project's Statuses. Every change goes through `StatusService`, which takes the project's `issue_counters` row lock first (the lock creating an Issue takes), so Status changes queue up with each other and with creates; it then reads Archived again (`409` with no code) and makes the default Statuses if the project has none. Rules:
  - A name is trimmed, then 1 to 30 characters without control characters (`400` with `errors.name`), unique in the project ignoring case (`409`, code `status_name_taken`; renaming a Status to the same name in another letter case is allowed). A category is `TODO`, `IN_PROGRESS` or `DONE` (`400` with `errors.category`).
  - At most 20 Statuses (`409`, code `status_limit`).
  - A new Status goes after the last Status of its category, so positions after it shift by one; positions stay 0, 1, 2, … with no gaps (a delete closes the gap).
  - Renaming or changing the category keeps the id, the position and the Issues; Issues in a renamed Status show the new name, but history entries keep the name they were written with.
  - Exactly one To do Status of a project is its **default**: the one new Issues start in (`is_default`, with a unique index per project and a check that it is `TODO`). The first To do Status is the default when the Statuses are made, and for projects from before it was stored (V31). `PUT .../statuses/{statusId}/default` makes another To do Status the default (`409`, code `default_needs_todo`, for any other category; the current default changes nothing). A project whose Statuses have none marked (put there outside the app) starts Issues in its first To do Status. Adding or reordering Statuses never changes it; if the default is re-categorised away from To do or deleted, the first To do Status left, in order, takes over.
  - A category change or a delete that would leave a category without a Status is `409`, code `category_needs_status`, checked before anything else changes.
  - `PUT .../order` takes every Status id of the project exactly once, otherwise `400` with `errors.statusIds`; nothing changes then.
  - Deleting a Status with Issues needs `moveTo`, another Status of the project (`400` with `errors.moveTo` when missing, unknown, of another project or the Status itself; this is checked even when there are no Issues to move). Each moved Issue is locked, gets a `status` history entry (old and new names, the actor) and a new `updatedAt` (not a new `version`), and `IssueChanged` with `status` is published for it, all in the delete's transaction. If an Issue moves into the Status while it is being deleted, the delete is `409` and nothing changes.
  - Unknown Statuses are `404`, like non-Members and unknown projects. An Archived project refuses every change with `409`.
- **Fields.** Type is `Story`, `Bug` or `Chore`. Title: surrounding whitespace removed, then 1 to 255 characters, no control characters. Description: optional Markdown of at most 50,000 characters, stored as typed (the web app sanitises it when rendering). Priority is `Urgent`, `High`, `Medium` or `Low`, `Medium` when omitted. Invalid fields give `400` with `errors` keyed by field, like `projects`.
- **Starting Status.** A new Issue starts in `statusId` when given (one of the project's own Statuses, otherwise `400` with `errors.statusId`), else in the project's default Status.
- **Rank.** Each Issue has a Rank, its place in its project's single manual order (ADR 0012). The server keeps it as a text key (`RankKeys`, fractional indexing in base 62) that clients never see or send: the Issue has no rank field. A new Issue goes after the project's last Issue, so at the bottom of its Status's column; its key is made under the `issue_counters` row lock creating already takes, so ranks are unique in a project. Moving an Issue to another Status, with `PUT .../status` or because its Status was deleted, keeps its Rank.
- **Reordering.** `PUT .../rank` with `{after?, before?}` (Issue keys of the cards directly above and below the drop, as the client saw them) places the Issue directly after `after` when given, else directly before `before`, else keeps its Rank; `200` with the Issue. "Directly" means in the project's whole order, so Issues a filter or another column hides stay where they are. It is best effort and never refused because of a neighbour: one that is the Issue itself, was deleted since (its number was taken once) or has moved to another Status than the Issue is ignored, and with none usable the Rank is kept. A neighbour that never existed, of another project or not an Issue key is `400` with `errors.after` / `errors.before`. A Rank change takes the `issue_counters` row lock (before anything else), so two drops never get the same key; when the key made is longer than 50 characters, the project's keys are rewritten evenly in the same transaction, in the same order. A reorder is silent: no history entry, no `IssueChanged`, and `updated_at` and `version` stay. With `statusId` (a drop in another Board column; clients send it only when the Status changes) the Issue first moves to that Status through the same path as `PUT .../status`, under the project lock and in the same transaction: the same `status` history entry, `updated_at` and `IssueChanged` (so the same Notifications), and the neighbours are then looked for in the new Status. A Status of another project is `400` with `errors.statusId`, and a refused neighbour undoes the move too, so a `400` changes nothing. A drop into an empty column (no neighbours) changes the Status and keeps the Rank. Permission: the same as moving (`issues:issue:edit`, with Scope Own meaning Reporter or Assignee), `404` for unknown Issues and non-Members, `409` without a code for an Archived project.
- **Reporter** is the creating User and never changes. **Assignee** is optional and must be a Member of the project: otherwise `400` with `errors.assigneeId`.
- **Archived projects** refuse new Issues and every edit with `409`; reading, including history, still works. `issues` asks `projects` before each write.
- **Editing.** Title, description, type and priority change with `PATCH`; only the fields sent change, and `null` or absent means unchanged. An empty description clears it. Validation is the same as creating. The Assignee is set with `PUT .../assignee`, where `null` unassigns, and must be a Member (`400` with `errors.userId`). The Reporter never changes (a `reporterId` in the body is ignored). Sending a field's current value changes nothing: no history, no event, no new `updatedAt`.
- **Version.** `version` guards title and description. It is required when the title or description sent really differs from the current one (`400` with `errors.version` if missing) and must equal the Issue's current one, otherwise `409` with code `issue_changed`; sending the current text again needs no version and never conflicts. Only a changed title or description raises it, so quick changes (type, priority, Assignee) need no version and never make someone's open text edit stale. The Issue row is locked (`SELECT ... FOR UPDATE`) while it is compared and changed, so of two edits with the same version one wins and the other gets `409`.
- **History.** Creating writes a `created` entry (actor = the Reporter, no before or after). Each changed field writes one entry with the actor and time: title, type and priority keep the old and new text, and a description entry keeps neither (it is up to 50,000 characters, so the entry only says it changed); an Assignee change keeps the old and new User ids, which `GET .../history` returns as display names ("Unknown user" if the User is gone). Entries from one edit share a time and come back in a fixed order (by field name, descending). History is returned newest first and is never edited.
- **Moving.** `PUT .../status` takes any Status of the Issue's project, in any direction; no version is needed and it never raises one. A Status of another project, an unknown one or a missing `statusId` is `400` with `errors.statusId`. Moving to the Status the Issue is already in changes nothing. A move writes a `status` history entry holding the old and new Status names as they were then, and `IssueChanged` lists `status`. It takes the same Issue row lock as other edits, and an Archived project refuses it with `409`.
- **Deleting.** `DELETE /api/issues/{issueKey}` takes the Issue row lock like every edit, writes an `issue_deletions` record (key, title, actor, time), then deletes the Issue; its history goes with it (`ON DELETE CASCADE`). The number is not reused because `issue_counters` only goes up. An Archived project refuses with `409`; an unknown or already deleted key is `404`. `GET .../history` of a missing Issue is `404` too.
- Unknown projects, unknown Issues and projects the User is not a Member of all give `404`. A Member without the needed Permission (or outside its Own) gets `403`. Missing or invalid access tokens give `401`; an unverified email gets the identity gate's `403`.

Contract: [openapi.yaml](openapi.yaml).

The Issue and its history are removed and a deletion record is kept. `404`, `409` (Archived).                                                                                                                                                                             |
| `PUT /api/issues/{issueKey}/rank`                                  | `{statusId?, after?, before?}` (Issue keys) → `200` with the Issue, moved to `statusId` when given and placed directly after `after`, else directly before `before`. `400` for a Status or neighbour of another project or an unknown neighbour, `403`, `404`, `409` (Archived). |
| `GET /api/projects/{key}/statuses`                                 | `200` with the project's Statuses in order `{id, name, category, position, isDefault}` (empty until its first Issue); `404`.                                                                                                                                                     |
| `POST /api/projects/{key}/statuses`                                | `{name, category}` → `201` with the Status, after the last one of its category. `400` field errors, `404`, `409` (Archived, `status_name_taken`, `status_limit`).                                                                                                                |
| `PATCH /api/projects/{key}/statuses/{statusId}`                    | `{name?, category?}` → `200` with the Status. `400`, `404`, `409` (Archived, `status_name_taken`, `category_needs_status`).                                                                                                                                                      |
| `PUT /api/projects/{key}/statuses/{statusId}/default`              | (no body) → `200` with the Status, now the default. `404`, `409` (Archived, `default_needs_todo`).                                                                                                                                                                               |
| `PUT /api/projects/{key}/statuses/order`                           | `{statusIds}` (all of them) → `200` with the Statuses in the new order. `400` `errors.statusIds`, `404`, `409` (Archived).                                                                                                                                                       |
| `DELETE /api/projects/{key}/statuses/{statusId}?moveTo={statusId}` | `204`; the Issues move to `moveTo`, which is required when there are any. `400` `errors.moveTo`, `404`, `409` (Archived, `category_needs_status`).                                                                                                                               |
| `GET /api/issues/{issueKey}/history`                               | `200` with entries `{id, actor, at, field, before, after}`, newest first (`field` is `created`, `title`, `description`, `type`, `priority`, `assignee` or `status`); `404`.                                                                                                      |

**Finding Issues.** Parameters, all optional, combine with AND; an empty result is a normal `200` with `total` 0.

- `status`: a Status name, ignoring case. `category`: `TODO`, `IN_PROGRESS` or `DONE`. `type` and `priority`: as on create.
- `assignee`: a User id, `me` (the caller) or `none` (unassigned).
- `q`: split on whitespace; every word must appear in the title, in any case. `%`, `_` and `\` in a word are plain text. At most 10 words and 200 characters, otherwise `400`.
- `sort`: `updated` (default, most recently updated first), `created` (newest first), `priority` (Urgent first, then most recently updated) or `rank` (the project's manual order, as the Board shows it). Ties end with the highest number first (`rank` has none: Ranks are unique in a project), so paging never repeats or skips an Issue.
- `page` (from 0, default 0) and `size` (1 to 100, default 50). A page beyond the last is empty. `total` counts the matches across all pages.

**Counting Issues.** `.../issues/counts` takes the same filters and refuses them the same way. `total` counts every match; `statuses` (keyed by Status id), `categories`, `types` and `priorities` count the matches per value, each leaving out its own field's filter, so with `type=Bug` the other types still show what choosing them instead would give. Values with no match are left out. The web app's Filter menu, its count and the Issues tab's count use it.

**Issue totals per project.** `GET /api/issues/stats` gives the Projects table its Open issues, Progress and Updated in one request, whatever the number of projects: the projects come from `Projects.memberProjects` (membership is all viewing Issues needs), then one grouped query counts each project's Issues and those in a DONE Status, with the latest `updated_at`, and another the latest deletion; `updatedAt` is the later of the two.

An Issue is `{id, key, number, type, title, description, priority, status: {id, name, category}, reporter: {id, displayName, avatarUrl}, assignee: {…} | null, createdAt, updatedAt, version}`. `version` starts at 0. Times are in microseconds, as the database keeps them.

## Web app

**Create Issue**, in the header every project tab shares (see projects), hidden for an Archived project or a User who may not create Issues, opens a window: Issue type, Title, Markdown Description, Priority and Assignee. Until the project's Members can be listed, the Assignee choices are Unassigned and the User themself. Field errors appear on their fields; success shows a toast and opens `/issues/:issueKey`. A create that finishes after the User has left the page shows a toast and does not navigate.

`/projects/:key/issues` (the project's **Issues** tab, the one `/projects/:key` opens) shows the project's Issues in one of four views, kept in the address (`view`) and, per project, in the browser: **List** (the default; grouped under each Status), **Board** (a column per Status; dragging a card up or down its column reorders the Issue and dragging it between the cards of another column moves it there, with a mouse, a finger or the keyboard (below); built on dnd-kit; each column ends with **Add issue**, which opens Create Issue for that Status, sends `statusId` and stays on the Board), **Table** (a sortable table, paged at 50 a page; Priority and Updated sort on the server) and **Swimlanes** (the Board grouped by Assignee, labelled "Assignee"; a card reorders within its lane's cell and moves to another column of its lane, never to another lane). The Board, Swimlanes and List ask for each Status's Issues separately (`status` by name, up to 100 each, "Showing n of total" when there are more), always in Rank order (`sort=rank`, whatever sort the address names; only the Table sorts).

**Reordering on the Board and in the Swimlanes.** The columns are sortable lists (dnd-kit sortable): while a card is carried in its own column, the other cards slide apart to open a gap where it will land. A drop on a card puts the Issue in that card's place and sends the keys of the cards directly above and below it (`after`, `before`) with `PUT .../rank` (`useReorderIssue`); a drop on a column's bare space counts as a drop on its nearest card. A drop in another column goes through the same request with that column's `statusId` (below). The card shows in its new place at once and goes back, with an error toast ("Couldn't reorder NIM-3: …"), if the server refuses. Reorders share the in-flight count of moves: the lists, counts and totals refresh once the last of several quick drops is answered. A card the User may not move can't be dragged but cards can still be dropped around it.

**Keyboard and screen readers on the Board.** Space lifts a focused card (Enter still opens it); Up and Down move it one place in its column, Left and Right to the neighbouring column at the same index (about the same height), where the gap opens; Space (or Enter) drops it there and sends that place's neighbours, with the new Status when it changed; Escape puts it back and sends nothing. A drop where it was lifted sends nothing, and after a drop in another column the focus stays on the card there. The place is kept as a Status and an index (`issues/keyboardDrag.ts`, made to be reused by the Swimlanes, List and Table), not worked out from boxes, and is read against the columns as they are at each key and at the drop, so a refresh while a card is carried is followed; collision detection points at the card that place names. The drag state belongs to each Board. A live region (`aria-live="assertive"`) says what happens: "Picked up NIM-12 at position 3 of 8 in In progress.", "NIM-12, position 4 of 8 in In progress" at each move (counting the whole column, not only the cards shown), "NIM-12 is already first in In progress" for a key that can't move it further, "Dropped NIM-12 at …" and "NIM-12 was put back at …"; a pointer drag is said the same way. dnd-kit's own announcements are off, and each card carries instructions for screen readers. A card the User may not move can't be lifted. The Swimlanes work the same way inside a lane: each lane's cell (an Assignee in a Status) is a sortable list, a drop between its cards, or between the cards of another column of the same lane, sends those neighbours (and the new `statusId`) with `PUT .../rank`, and the keyboard's Up, Down, Left and Right stay in the lane (the live region names the cell: "NIM-12, position 2 of 3 in Dana, To do"; their instructions say so). A drop in another Assignee's lane puts the card back and sends nothing: the Swimlanes never change the Assignee.

**Moving on the Board.** While a card is carried it tilts a little, and the column under it shows a card-sized dashed gap where it will land; only a drop that changes the Status shows one. On the Board the gap stands among the cards: over a card, above it when the carried card's middle is above that card's middle and below it otherwise; in an empty column, at the top. A drop sends that column's `statusId` and the cards around the gap (`after`, `before`) in one `PUT .../rank` (`useReorderIssue`), and shows the card there at once, before the server answers; it goes back, with an error toast ("Couldn't move NIM-3 to In progress: …"), if the server refuses. A drop in an empty column sends no neighbours, so the server keeps the Rank. In the Swimlanes the gap stands among the cards of the card's own lane in that column, and a drop is sent like the Board's, with the cell's neighbours. The carried card glides into its new place, overshooting a little and settling, starting at once from where the dashed gap was for a move to another column (a reorder waits a tick for the Board to show it, then finds the card), and once there an orange line runs once around its outline; a card that went back is not traced, and with reduced motion there is no animation. The card itself stays hidden until the carried card lands on it, so it never shows back where it was or twice for a frame. While several moves are on their way, a move that finishes doesn't refresh the lists, since a refresh then could show a later move's card where it was; the last one to finish, whether it worked or not, refreshes the lists, counts and Projects table totals of every project a finished move changed.

The toolbar (design "Issues toolbar", F2) is one row that never changes height: **Search issues** (applied once typing pauses; `/` focuses it from anywhere but a field; × or Esc clears it), **Filter**, **Mine** and **Unassigned** (one `assignee` filter, so picking one turns the other off; orange while on), and on the right the matching count ("1 issue", "12 issues", from the counts endpoint) and the view switcher (icons, the open view also named). **Filter** opens a two-pane menu: Status, Category, Type and Priority on the left, the chosen field's values on the right with their counts, one value per field (picking the chosen value again clears it; **Clear** clears the field). ↑ ↓ move within a pane, ← → switch panes, Enter picks, Esc closes and gives focus back to Filter. Its badge counts the menu fields applied (not the search or the quick filters). Applied menu fields show as tokens on a second row ("Type is Bug", × removes one; **Clear all** removes them all, keeping the search and the quick filters), shown only when there are any. Every filter is kept in the address so a filtered view can be shared; values it does not recognise are ignored. A Status filter keeps every Board column but asks only for that Status, the others showing 0. When nothing matches, the Board and Swimlanes keep their columns under a message: filters name themselves ("Status is In progress and Category is To do. Try removing one.") with **Clear filters** (menu and quick filters, keeping the search); a search alone says "No issues match “login”" with **Clear search**. While loading, a skeleton in the open view's shape stands in. A refresh that fails while the view still shows its last answer (in the Board, Swimlanes and List, any shown column's) says "Couldn't refresh these Issues. Showing the last loaded list." under the toolbar, with **Try again**, which asks again for what failed. On a phone the search takes its own row, the views fold into one menu button, the tokens scroll sideways, and Filter opens a bottom sheet (fields, then a field's values, with **Show n issues**). An Archived project says "Archived · read-only" by its name and offers no Create Issue, Add issue or dragging; search, filters and views still work. An empty project offers **Create Issue** again. Rows and cards show the title, key, type, priority (signal bars: three red for Urgent, three orange for High, two for Medium, one muted for Low), Status and Assignee, and open `/issues/:issueKey`. The Issues tab shows the project's number of Issues.

`/projects/:key/settings/statuses` (the project's **Settings** tab, shown to a User who may manage Statuses; for an Archived project the page is read-only) has one card for each category (To do, In progress, Done) with its colour dot, its Issue count (the sum of its Statuses', from `GET .../issues/counts`) and a line about what the category means. A Status is a plain row: a colour dot, its name, a **Default** badge on the project's default Status, and its Issue count. The drag handle, the pencil and the ⋯ menu show on hover or keyboard focus (always, where there is no hover). Clicking the name or the pencil renames it in place: Enter or leaving the field saves, Esc cancels, and a refusal shows under the field. **+ Add status**, at the bottom of each card, opens a row in that category with a name field and Add / Cancel (Enter adds, Esc cancels). The ⋯ menu has Rename, **Category** (a submenu of the three, the current one checked), **Set as default** (To do Statuses only, so it is disabled with "To do only" for the others, and for the default itself) and **Delete…**. Delete is disabled, with the tooltip "Each category needs at least one status.", for the only Status of a category, and so is dragging it. A row is dragged by its handle, with a mouse, a finger or the keyboard (dnd-kit), within its card or into another card to change its category: the card it is over is tinted with a dashed edge and a dashed slot shows where the row lands. A drop saves at once: a new category with `PATCH` and then the order with `PUT .../order`, which is always the To do, In progress and Done cards' rows in turn, so the Board's columns follow the cards. Changes are sent one at a time and the lists refresh when the last is answered; a refusal is a toast and the page is put back. **Delete…** asks "Delete “In review”?": for a Status with Issues, "Move its issues to" (the first other Status of the same category chosen) and a button saying how many move ("Delete and move 2 issues"); the Issue count comes from `GET .../issues?status=<name>&size=1`. Refusals (`409`, `400`) appear as a toast or on the field. A project with no Statuses yet says they are made with the first Issue or the first added Status. A project has at most 20, after which every + Add status is disabled.

`/issues/:issueKey` shows the key, type, title, description, Status, priority, Reporter, Assignee and the history, newest first. **Edit title** and **Edit description** open an inline editor with Save and Cancel; they send the `version` the page was opened at. If the Issue's version changes while the editor is open (a refresh saw it), or the save is refused as stale, an alert says "This Issue changed since you opened it", Save is disabled and **Load the latest** discards the edit and reloads, but the typed text stays on screen until then. Status, Issue type, priority and Assignee are selects that save as soon as one is chosen; the Status select lists the project's Statuses in order, with the current Status's category beside it. Until the project's Members can be listed, the Assignee choices are Unassigned, the User themself and the current Assignee. The description is rendered with `react-markdown` and `remark-gfm` (checklists, tables): raw HTML is never rendered (a pasted `<script>` shows as text) and unsafe link addresses such as `javascript:` are dropped. **Delete Issue** asks "Delete NIM-12?" in a window; **Delete** removes it, shows a toast and returns to the project's Issues, while a refusal (for example an Archived project) is shown as a toast and the Issue stays. Unknown keys, and Issues of projects the User is not in, show "Issue not found." Every page reads `GET /api/access/me/permissions?project=` (`useIssuePermissions`) and hides what the User can't do: Create Issue, Manage Statuses (the Statuses page shows "You can't manage Statuses."), Edit title/description and Delete Issue, with the detail selects and Board drags turned off for Issues they may not edit. Own is worked out in the browser from the Reporter and Assignee; the server checks every action anyway.
