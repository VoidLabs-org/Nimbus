# desktop

The Electron app (`apps/desktop`): a window around the web app (`apps/web`). It is not a backend module, so there is no public interface or events here; this describes how it works now. Features of the Desktop app are planned in #177; this file grows with each ticket.

## Where it loads Nimbus from (ADR 0007)

The window opens `NIMBUS_URL`, read when the app starts. The default is `http://localhost:3000`, the dev server, so `pnpm dev:desktop` (API, web and the window) needs nothing set. It must be an `http` or `https` address; anything else shows an error box naming the variable and quits.

| Command                                              | Does                                                                            |
| ---------------------------------------------------- | ------------------------------------------------------------------------------- |
| `pnpm dev:desktop`                                   | Starts the API, the web dev server and the window on it                         |
| `NIMBUS_URL=https://... pnpm --filter desktop start` | Opens the window on another Nimbus (a hosted one, or someone else's dev server) |

The window shows the website exactly as a browser would, so `/api` calls, the refresh cookie and Google and GitHub sign-in work the same. There is no copy of the web app inside the Desktop app.

## The window

- **Navigation.** The window may navigate within Nimbus's origin, and within the origin of the page it is showing (`isNavigationAllowed` in `src/nimbus-url.js`), so a Google or GitHub sign-in page, which Nimbus redirects the window to, can submit its own form. A hop from one site to another (a Nimbus page linking to a stranger, a provider page linking to a third site) is blocked, as is any non-http(s) address. A `window.open` or `target=_blank` link to an http(s) address opens in the default browser. Redirects through a provider and back are not page navigations, so they are not checked. The window has no address bar or back button; closing and reopening the app returns to `NIMBUS_URL`.
- **Security.** `contextIsolation` and `sandbox` are on. The page gets only `window.nimbusDesktop` from the preload script (`src/preload.cjs`). The web app treats its presence as "this is the Desktop app".
- **Signing in** happens in this window, as in the Claude and Notion apps: the signed-out pages (Login, Register, Two-step sign-in, Forgot password, the provider return page, Session expired) show centred in it, without the Sidebar or Tabs, and signing in turns it into the app. Login, Register, Forgot password, Two-step sign-in and Verify your email show the form alone, centred under the Nimbus logo (design "Nimbus Desktop v2", sign-in; `AuthLayout`), without the website's Nimbus panel. There is no separate sign-in window (#181 dropped the one #177 planned).
- **Opening.** The window opens hidden and shows once the page has drawn itself (`ready-to-show`), so it never appears as a blank rectangle first. A page that fails to load shows at once (a load another navigation replaced, `ERR_ABORTED`, is not a failure), and one that hasn't drawn after 3 seconds (a slow or stalled server) shows anyway, so starting Nimbus never seems to do nothing.
- **Its place** (`src/windows.js`). The window's size, position and whether it was maximized are saved in the user data folder (`window-state.json`) when it closes, or when Windows shuts down or signs out with it open. On opening it goes to the screen most of it was on, made no bigger than that screen (but never under 800×560) and moved onto it (after undocking from a large monitor, say), so it can always be dragged and resized; on no screen at all (one that was unplugged) it opens centred at 1280×800. Either way it is maximized again if it was.
- **One at a time.** A second launch brings the running Nimbus's window forward (restoring it if minimized, and showing it maximized if it was left so while it was still loading) and quits, so two copies never overwrite each other's saved Tabs or window place. On macOS, where Nimbus keeps running with no window, a second launch opens one.
- **Frame** (`windowChrome` in `src/chrome.js`). The window opens at 1280×800 and is never smaller than 800×560. The title bar is hidden (`titleBarStyle: "hidden"`), so the page draws its own frame, as in the design (2a): the Sidebar down the left and a 46px title row over the page holding the Tabs, both in the theme's surface colour, with the page in its background colour beside them. The top 46px (the Sidebar's top row and the title row) are the drag area; the Tabs and buttons in them opt out. On Windows the OS draws its window buttons over the right end of the title row (`titleBarOverlay`, see-through, symbols coloured for the page's theme); on macOS the traffic lights are inset into the Sidebar's top row; Linux keeps the native frame, with the title row under it. Pages outside the shell (Login, Register, the session check, Session expired) get a 46px drag strip across the top instead (`DesktopFrame`), and start below it, clear of the window's buttons; not on Linux.
- **Icon** (`appIconFile`). The window, taskbar and Dock show the Nimbus icon from `apps/desktop/assets`, in the version for the mode the taskbar or Dock is drawn in (the dark mark on light, the light mark on dark), not the page's theme. On Windows that is Windows mode (`SystemUsesLightTheme`, read with `reg query`, `windowsTaskbarMode`), which can differ from the apps' mode Electron reports: by default Windows is dark and apps light. Elsewhere it is the OS's mode. It is looked at before the window opens, when the OS changes theme and, on Windows, when the window comes forward. The files are copies of `apps/web/public/nimbus-icon-*.png`.
- **Menu** (`menuTemplate`). macOS has a minimal menu: the app menu, Edit, View (actual size, zoom in and out, full screen) and Window. Windows and Linux have Edit, View and Window (Minimize, and Close on Ctrl Shift W, since Ctrl W closes a Tab) too, but no menu bar: their shortcuts work, and the Nimbus icon at the top left of the page pops the menu up under itself (`showAppMenu`), as Notion's icon does. Reload, force reload and developer tools are only there with `--dev` (which `pnpm dev:desktop` passes); without it developer tools are off altogether.

## `window.nimbusDesktop`

| Member              | What it is                                                                                                                                                                                                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `platform`          | `"darwin"`, `"win32"` or `"linux"`                                                                                                                                                                                                                                                               |
| `setTheme(mode)`    | The page says whether its theme is `"light"` or `"dark"`. On Windows, main colours the window buttons to match. It does not set `nativeTheme.themeSource`, which would also fix the page's `prefers-color-scheme` and stop the System theme following the OS. Only Nimbus's own pages are heard. |
| `showAppMenu(x, y)` | Pops the app menu up at that point in the window (Windows and Linux; whole pixels inside the window, anything else is ignored). Only Nimbus's own pages are heard.                                                                                                                               |

The preload script runs on every page the window shows, a provider's sign-in page too; main ignores `nimbus:theme` messages from any origin but `NIMBUS_URL`'s (`isNimbusPage`).

## The shell (web app)

When `window.nimbusDesktop` is there, signed-in pages use `DesktopShell` (`apps/web/src/shell/DesktopShell.tsx`) instead of the browser's navbar (`AppShell`). It is loaded as its own chunk, so the browser never downloads it, and the browser's navbar is unchanged. If the chunk can't load (a redeploy removed it while the window stayed open, or the connection dropped), the navbar shell is shown instead of a blank window. `DesktopFrame`, on every page, sends the theme to the window (`setTheme`) and sets `data-desktop` on the root element for the frame's stylesheet.

- **Sidebar.** On the left: Home and Projects at the top; Settings and the account (picture, name and email, opening the account menu with Sign out, upwards) at the bottom, with a place for the Notification bell beside the account once Notifications exist. The links are the same `DESTINATIONS` as the browser's navbar. There is no brand row, as in other desktop apps; on Windows and Linux the Nimbus icon at the top left opens the app menu. Settings opens the Settings overlay (below); it is highlighted while the overlay is open. The open page's link is highlighted.
- **Folded.** Like the Claude app's, the Sidebar folds away completely and the page gets the whole width. The Sidebar button stays in one place at the top left, whether the Sidebar is open or folded (after the Nimbus icon on Windows and Linux, just right of the traffic lights on macOS); it and the shortcut switch between open and folded. The choice is kept on this computer (`localStorage` key `nimbus-sidebar`, default open). While folded, resting the pointer on the button for 300ms peeks the Sidebar out over the page without opening it for good; it goes when the pointer moves onto the page, on Esc, or when a page is opened from it, and clicking the button while peeking opens it. While the window is under 960px wide the Sidebar folds itself without changing the choice; the button or shortcut opens it until the window is widened.
- **Appearance.** In the Desktop app the Appearance page has only the theme: there is no navbar to position, and the Sidebar folds with its button or the shortcut, which is remembered. The theme is picked from tiles (`ThemeTiles`, design "Nimbus Desktop v2", Settings → Appearance): Paper, Ink and System, each with a preview of its page colour and the chosen one ringed. The glass themes (Fog, Slate) don't suit a window, so the Desktop app has only the flat ones (`flatOnly` on `NimbusThemeProvider`): a Fog or Slate saved earlier shows as Paper or Ink, from the first paint (`index.html` applies the saved theme before React does), and picking Paper or Ink sets only light or dark, so the saved glass choice stays. The website keeps all four.
- **Toasts** appear bottom right.

## Tabs

The title row holds the User's Tabs (design 2a), as a browser does: each shows a page, and opening a page shows it in the selected Tab; a new Tab opens only when asked for (`useTabs` and `TabRow` in `apps/web/src/shell`, the rules in `tabs.ts`).

- **Opening a page** the usual way (a link, the Sidebar, Back) shows it in the selected Tab, which takes its name. The query string isn't kept. Clicking a Tab selects it and opens its page.
- **A new Tab** opens with Ctrl click (⌘ click on macOS) or a middle click on a Nimbus link, "Open in new tab" in a link's right-click menu, or the + after the Tabs (Home). It goes right after the selected Tab and is selected. The same page may be open in more than one Tab. Those clicks on a Settings link open Settings, which is never a Tab; another site's link still opens in the default browser.
- **Names.** Like the page's breadcrumb: its last crumb (`tabTitle` in `crumbs.ts`), so a project shows its name. `BreadcrumbTrail` hands it to the shell (`TabTitleContext`); until it loads, a project's Tab shows its key and the others their Sidebar name (an address that is no page, "Not found"). Long names are cut short, in full on hover.
- **Closing.** Its ✕, a middle click, Ctrl W (⌘ W on macOS) for the selected one, or its right-click menu. Closing the selected Tab opens the one after it, or else the one before; closing the last opens Home in a new Tab. Closing another Tab leaves the page as it is. Ctrl Shift T (⌘ ⇧ T) reopens the last closed Tab where it was, for as long as the window is open.
- **A Tab's right-click menu** (design "Nimbus Desktop v2", context menu): Close tab, Close other tabs, Close tabs to the right, Duplicate tab (a copy after it, selected) and Reopen closed tab. "Move to new window" waits for more than one app window. Its items act on the Tabs as they are when picked, not as they were when it opened.
- **A Sidebar link's right-click menu** (Home, Projects): Open, Open in new tab and Copy link (the page's full address). Projects and Issues bring their own menus.
- **Switching** is a normal page change: no page is kept alive in the background, so a page's own state (a half-typed form) does not survive it; its data comes back from the TanStack Query cache. A Tab action (selecting, closing, opening a new Tab, reopening) replaces the window's address rather than adding to its history, so Back never loads one Tab's page into another; Back and Forward go through the window's history, not a Tab's own. While Settings is open over a page, or shows as a page because its overlay couldn't load, the selected Tab keeps its page.
- **The row** is only as wide as its Tabs and the +, so the rest of the title row (and the window buttons' area) stays the drag area. When they don't fit it scrolls sideways, keeping the selected Tab in view. The selected Tab is in the page's colour and curves out into the page at its bottom corners, as a browser's selected tab does.
- **Kept per User.** The Tabs (each with an id, its page and name) and the selected one are kept on this computer under `nimbus-tabs:<User id>`, so another User signing in here never sees them, and are restored when the shell starts for that User: after a restart or a new sign-in. Starting on Home (the window's start address, or where signing in lands) goes back to the Tab the User was on; any other start address opens in it as usual. A restored Tab whose address is no longer a page (`isTabPath`: Home, Projects, a project) is dropped; a project the User may no longer open keeps its Tab and shows Not found, as that page decides. Signed-out pages are outside the shell, so they are never in a Tab.

## Jump

Jump opens a page or runs a command by name (`Jump` and `jumpTargets` in `apps/web/src/shell`, design "Nimbus Desktop v2", Search). The "Search or jump to…" box at the right end of the title row (design 2a, naming its shortcut) or Ctrl K (⌘ K on macOS), from anywhere, opens it: a panel near the top of the window, with the search field, the list in groups and a footer of keys (↑↓ Move, ↵ Open, Ctrl ↵ New tab, `>` commands).

- **Nothing typed.** "Go to": Home, Projects and Profile; "Actions": the first four actions.
- **Typing.** The pages, Settings pages and actions whose name holds what was typed, ignoring case, under the headings Pages, Settings and Actions, those starting with it first; the matching part of each name is marked. Nothing matching says "No results for …" and points to the commands.
- **Commands.** Typing `>` first keeps only the actions, with a "Commands" pill in the field: New project (opens Projects), Switch to Paper or Ink theme, Fold or Open the Sidebar (Ctrl `\`), Open Settings (Ctrl `,`) and Sign out, which asks "Sign out?" first, as the account menu does (`SignOutDialog`).
- **Pages.** The Sidebar's (Home, Projects) and the Settings pages the User may open, from the same `settingsGroups` as the Settings overlay: Roles & access and the Audit log only with their Permissions. Pages only for now; projects, Issues, recent items and an Issues (`#`) search come with their own tickets.
- **Keyboard.** The arrow keys move the highlight, round the ends, while the focus stays in the search field (a combobox over a listbox in groups, for screen readers); Enter or a click opens the highlighted item, ↵ showing on it; Esc, the Esc badge or a click outside close it, and the focus goes back to where it was. Each opening starts empty.
- **Where a page opens.** In the Tab already showing it, if another Tab does (it is selected); otherwise in the selected Tab, as a link would. Ctrl Enter or Ctrl click (⌘ on macOS) opens it in a new Tab. A Settings page opens in the Settings overlay over the page.
- **The box** gives way to the Tabs in a narrow window, down to its icon and shortcut.

## Settings overlay

In the Desktop app, Settings opens over the page the User is on instead of as pages (`SettingsOverlay`, design "Nimbus Desktop v2" 2c). The browser keeps the Settings overview and its pages.

- **Opening.** Settings at the bottom of the Sidebar, or Ctrl `,` (⌘ `,` on macOS) from anywhere, opens it on Profile.
- **Inside.** A panel centred in the window over the dimmed, blurred app, laid out like the Claude app's Settings: a header row ("Settings" and the ✕) over two columns, each scrolling on its own. On the left the Settings pages, Account (Profile, Security, Appearance) for everyone and Workspace (Roles & access, Audit log) only for Users who may open them, from the same `settingsGroups` as the overview; on the right the open page. A page's breadcrumbs start inside the overlay (`overlayCrumbs`): a page the list opens has none, a Role starts at Roles & access.
- **Closing.** Esc, the ✕ or a click on the dimmed app goes back to the page behind, the way Back does: back through the history entries Settings added, so Back afterwards doesn't open Settings again. A Settings address opened directly is replaced by the page behind. Esc closes Settings only when pressed inside it and not in a text field, so a page's own dialog or menu, drawn outside the panel, gets its Esc first. While Settings is open, Ctrl `,` does nothing, so the page open in it stays.
- **Addresses.** The overlay is how the Desktop app shows any `/settings/...` address (`isSettingsPath`) once the User is signed in and verified (not while a new email is being confirmed), so links, Back and a restored page keep working. `AppRoutes` keeps the page behind: the last signed-in address that wasn't Settings, for that User (never a signed-out page such as Login or Session expired), or Home for a Settings address opened directly. `/settings` itself opens Profile, and `/settings/password` Profile's password window.
- **Tabs.** A Settings address is never a Tab of its own; Tabs hold the pages behind the overlay. While Settings is open, the Tab shortcuts do nothing.
- **Window.** The overlay is drawn after the window's drag areas and opts out of them, so its controls take clicks at the 800×560 minimum size too. Its chunk loads on first use; if it can't load, Settings shows as pages in the shell instead, so it stays reachable.

## Tests

`pnpm --filter desktop test` runs plain Node tests (`node --test`) for reading `NIMBUS_URL`, which navigations the window allows, which pages may call main, the window's frame and menu, and saving and restoring the window's place, without starting Electron. The Sidebar, the Tabs and Jump are tested in the web app (`DesktopShell.test.tsx`, `Tabs.test.tsx`, `Jump.test.tsx`) with `window.nimbusDesktop` faked.
