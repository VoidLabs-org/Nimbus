# identity

Owns **Users** and sign-in: registration, passwords, email verification, access tokens, refresh-token sessions and Linked identities (Google, GitHub). Terms are defined in [GLOSSARY.md](../../GLOSSARY.md). Users are global, not owned by a workspace ([ADR 0001](../adr/0001-global-users-tenancy-deferred.md)).

## Public interface

| Type          | Use                                                                                                                                                                                                                                                                                                                                                                                |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CurrentUser` | Inject it and call `id()` for the signed-in User's id (UUID) in a request. Outside an authenticated request it throws `AuthenticationCredentialsNotFoundException`, which becomes a `401`.                                                                                                                                                                                         |
| `Users`       | `findByEmail(email)` (any case, surrounding whitespace ignored) and `findAllById(ids)`, returning `UserSummary`: `id`, `email`, `displayName`, `avatarUrl` (the address of the Profile picture the User shows, null for initials; see Profile picture) and `emailVerified`. For other modules that need to look Users up, e.g. `access` checking that the admin email is verified. |

Everything under `identity.internal` is private to the module.

## Admin seed

At startup, when `NIMBUS_ADMIN_EMAIL` and `NIMBUS_ADMIN_PASSWORD` (in `apps/api/.env`, see `.env.example`) are both set and no User has that email, identity creates that User (display name `Admin`) and publishes `UserRegistered`. Otherwise it does nothing, so restarts never create a duplicate and changing the password in `.env` later does not change an existing User. The seeded admin's email counts as **verified**: whoever controls the deployment's configuration owns that address, so continuing with Google or GitHub later keeps their password and sessions. (An admin created by an earlier version stays unverified.) The seed gives no role by itself; `access` decides what an admin may do. The email and password must pass the same rules as registration (see Rules): one definition, the `@ValidEmail` and `@ValidPassword` constraints, is used by both, so the seed accepts exactly what registration accepts. A value that fails stops startup with a message naming `NIMBUS_ADMIN_EMAIL` or `NIMBUS_ADMIN_PASSWORD` (the password is never printed).

**When the admin changes their email, update `NIMBUS_ADMIN_EMAIL` to the new address.** Nothing special happens to the admin's email change: the User keeps their platform roles, but on the next restart the seed finds no User with the old address and creates a second admin with it and the `.env` password. The other way round, a User who changes their email to a free `NIMBUS_ADMIN_EMAIL` proved they own it with the code from that inbox, so `access` makes them Platform admin at the next startup by its usual rule; `EmailChanged` is not `EmailVerified`, so nothing happens before then.

## Authentication

- Every request needs a valid access token in `Authorization: Bearer <token>`, except the public endpoints below. Requests without one get `401`, except a browser page load: a `GET` or `HEAD` that names `text/html` (or plain text or an image) in `Accept`, which is redirected (`302`, `Cache-Control: no-store`) to the web app's `/login` on `PUBLIC_URL`. This is the same with one provider, two or none (the page also has the email form). Before, one provider started its sign-in directly and two fell back to a generated page on the API host. A request that accepts anything (`Accept: */*`, as `fetch` and `curl` send), names only other types, or is not a `GET`/`HEAD` (a form post, an update) gets the `401`.
- Access token: HS256 JWT, valid 15 minutes, `sub` = User id, `sid` = the id of the session it was issued in (tokens without one are refused by endpoints that need it). Signed with `JWT_SECRET` from `apps/api/.env` (base64, at least 32 bytes). The app refuses to start without it.
- **Email verification gate.** A User who registered with a password is an **Unverified User** until they verify (see Email verification). Their access token works only for an exact list of method and path pairs: `GET /api/users/me`, `POST /api/auth/verify-email`, `POST /api/auth/verify-email/resend`, `POST /api/auth/logout`, `POST /api/auth/refresh`, and the public sign-in endpoints (register, login, providers, the OAuth redirects, forgot-password), which a stale token may ride along with. Every other endpoint, in any module and anything added under `/api/auth/` later, answers `403` with `code: email_unverified` (a problem detail). A new endpoint an Unverified User needs must be added to that list on purpose. Access tokens carry an `ev` claim (true when the email was verified at issue time). A token with `ev` true passes without a lookup; any other token (false, or issued before the claim existed) is checked against the User's row on each request, so verifying takes effect at once without a new token. The web app asks for a fresh token right after a correct code, so the lookups stop for it. Users created by Google or GitHub, and the seeded admin, are verified from the start and never gated.
- Public endpoints: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`, `POST /api/auth/password-reset`, `POST /api/auth/password-reset/confirm`, `POST /api/auth/two-step`, `GET /api/auth/providers`, and the two OAuth endpoints under `/api/auth/oauth2/` below.
- The API is stateless: no HTTP session, no CSRF tokens (Bearer tokens can't be forged cross-site). The one exception is the OAuth handshake below, which uses a short-lived HTTP session that is dropped when the handshake ends.
- Responses carry `Cache-Control: no-store`.

## Sessions and refresh tokens

- Register and login start a **session** (a refresh-token family) for that browser and set its first refresh token in a cookie: `refresh_token`, `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`, `Max-Age` until the token expires. The refresh token never appears in a response body.
- Refresh tokens are 256 random bits (base64url), stored only as SHA-256 hashes.
- Each refresh token works once. `POST /api/auth/refresh` marks it used and sets a new one in the same session (rotation).
- Presenting a used token means it was copied: the whole session is revoked, so neither copy works any more. Other sessions of the same User are not affected.
- Expiry: a token expires 30 days after it was issued (`nimbus.auth.session-idle-timeout`), so a session lives as long as it is used at least every 30 days, but never more than 90 days after sign-in (`nimbus.auth.session-max-age`).
- Each session keeps the `User-Agent` of the request that started it (`sessions.user_agent`, cut to 512 characters; null when the browser sent none and for sessions from before it existed). It is set at password sign-in, registration and the Google/GitHub callback, and a refresh never changes it. No IP address or place is stored. `GET /api/users/me/sessions` turns it into a label ("Chrome on Windows") with uap-java when the list is read, so a newer parser list also names old sessions; the phone variants are shown as one browser ("Mobile Safari" as "Safari") and "Mac OS X" as "macOS". What the parser can't place is "Unknown browser", or just the half it can place ("Firefox", "Unknown browser on Linux"); never "Other".
- Sign-out revokes the session (`sessions.revoked_at`), so every token of it stops working, then clears the cookie. Access tokens already issued stay valid until they expire (up to 15 minutes); they are not denylisted.
- A `401` from `/refresh` also clears the cookie (`Max-Age=0`), so the browser stops sending a dead token.
- The cookie is the only credential for `/refresh`, so it also requires `X-Requested-With: nimbus` (`403` without it). Cross-site forms can't set that header.
- Known trade-off: two refreshes sent at once with the same cookie (e.g. several tabs restored together) count as reuse and end the session. The web client sends one refresh at a time per tab, and only a `401` from `/refresh` ends the User's visit: it opens `/session-expired` ("Your session expired.", no navbar), whose **Sign in** returns them to the page they were on. A `429` or an outage doesn't; when the sign-in check on load fails that way, the web app shows its offline page (no connection) or server-error page, each with a way to try again.
- **Cleanup:** a scheduled job deletes sessions that ended more than 7 days ago (`nimbus.auth.session-retention`), meaning revoked (sign-out, token reuse, a provider link, a password change or a password reset) or past their 90-day cap. Their refresh tokens go with them (`ON DELETE CASCADE`). It runs every hour (`nimbus.auth.session-cleanup-interval`, a fixed delay, first run one interval after startup) and logs how many sessions it removed. The same run deletes expired remembered browsers (see Two-step verification). Each delete takes at most 1000 sessions (`nimbus.auth.session-cleanup-batch-size`) and commits on its own, so a large backlog is cleared in small steps; `sessions.expires_at` and `sessions.revoked_at` are indexed for it. A session whose refresh tokens all expired from the 30-day idle timeout still counts as running until its 90-day cap (a revoked one counts as ended at once), so abandoned sessions keep their rows until then. A session still running is never deleted, however old its tokens are: reuse detection needs the used ones while the session lives. After deletion its cookie gets the same `401` as any unknown token. Written for a single API instance; two instances running it at once only repeat the same deletes.
- Access tokens outlive their session by up to 15 minutes, so an endpoint that must not be used from an ended session (setting a password) checks the token's `sid` against the session. Most endpoints don't.

## Linked identities (Google, GitHub)

"Continue with Google" and "Continue with GitHub" are backend-driven authorization-code flows (Spring Security `oauth2Login`). Google uses scopes `openid profile email`; GitHub uses `read:user user:email`. `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` and `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` come from `apps/api/.env` (see `.env.example`); without a provider's id that provider is off, and with neither there is no OAuth wiring at all. The redirect URI to register at each provider is `<PUBLIC_URL>/api/auth/oauth2/callback/<google or github>`. `PUBLIC_URL` (setting `nimbus.auth.public-url`, default `http://localhost:3000`, the Vite server) is the address people open Nimbus at. It is configured rather than read from the request, because behind the dev proxy or a load balancer the request's host is not the browser's. The redirects after the handshake (`/auth/callback`, `/login?error=...`) go to it as well. Provider tokens are never stored. The handshake's HTTP session (`server.servlet.session.timeout`, 5 minutes, `SameSite=Lax`) is invalidated as soon as the handshake ends. A `returnTo` query parameter on `/api/auth/oauth2/<provider>` (the page the sign-in started from) is kept in that session only, never sent to the provider, and added to the redirect that ends the handshake (`/auth/callback?returnTo=<page>` or `/login?error=...&returnTo=<page>`). It is kept only when it is a path inside the app: one leading `/` (not `//` or `/\`), not `/` alone, no control characters (browsers drop tabs and newlines, so `/\t/evil.com` would become another host), at most 2048 characters.

Google's ID-token claims become an **external profile**: provider, provider user id (`sub`), email (lower-cased), email verified (`email_verified`), name, avatar URL. GitHub is plain OAuth 2 without an ID token, so its profile is read from two API calls made with the provider token (which is then dropped): `GET /user` gives the id (provider user id), `login` and `avatar_url`, and the name, which falls back to the username (`login`) when empty; `GET /user/emails` gives the email, which is the **primary** address, verified only if GitHub marks that address verified (a verified non-primary address doesn't count). A GitHub account with no verified primary email is refused with `email_unverified`. If the emails call fails the login fails (`failed`). A provider maps only to this shape; the rules below don't know about Google or GitHub.

Resolution, in this order:

1. The login is already linked (same provider and provider user id): sign in that User, whatever email the provider reports now.
2. The email is not verified (or missing): refused, `email_unverified`. Nothing is created.
3. A User with that email exists: the login is linked to them and their email is marked verified. If their email was **never verified** (they registered with a password), their password is removed and **all their sessions are revoked**, so whoever registered the email first loses access. A User whose email was already verified keeps their password and sessions. **Exception:** when that User has disconnected this provider (a row in `disconnected_providers` for them and the provider), nothing is linked and the sign-in is refused, `disconnected` (`/login?error=disconnected&provider=<provider>`); no password is removed and no session is revoked. The mark is per provider, not per provider account, and only rule 3 looks at it: rule 1 and rule 4 are unchanged, so the same provider account on another email follows the normal rules.
4. Otherwise a verified User with no password is created, the login is linked, and `UserRegistered` is published (only here; linking an existing User does not publish it).

The seeded admin counts as verified (see Admin seed), so linking a provider never removes the admin's password. Anyone else who lost their password this way, or never had one, sets it with `PUT /api/users/me/password` while signed in with the provider, or through forgot-password (see Forgot password), which keeps their Linked identities. Only a User whose email was never verified (a password sign-up) can have a password removed.

Every sign-in with a provider updates `avatar_url` (when the provider sends one), which a User who never chose a Profile picture is shown, so their picture follows the provider last used. Once they uploaded a photo, sign-ins still update `avatar_url` but no longer change what is shown (see Profile picture). The display name is never overwritten. A new User's display name is the provider's name made valid by the display name rule (the disallowed characters removed, stray joiners dropped, cut to 100 characters, since a provider sign-in can't be refused over a name), or the part of the email before `@` when nothing usable is left (and `User` as a last resort). A race that would create the same User or link twice ends in a unique-constraint violation and shows as `failed`.

Each Linked identity also keeps an **account name** to show the User, "Connected as ...": the Google email (lower-cased) or the GitHub username (`login`, which can differ from the name). It is set when the login is linked or the User is created, and refreshed on every sign-in with that provider so it follows a rename at the provider; a sign-in that brings none keeps the one we have. Identities linked before `account_name` existed (V15) stay null until their next sign-in. Nothing else is stored about the provider account.

On success the User gets a session and the refresh cookie like any other sign-in; no token is in a URL. A User with Two-step verification gets neither yet (ADR 0005): the callback sets the `two_step_pending` cookie, as `POST /api/auth/login` does, and redirects to `/login/two-step` (with `returnTo` when one was kept), where a Sign-in code or a Recovery code finishes the sign-in. The callback finds that User by the resolution rules above without changing anything (`ExternalSignIn.whoSignsIn`): a provider account that would be linked by email is linked, and the avatar and account name refreshed, only once the code is right, in the same transaction as the Session. The pending sign-in holds the provider's profile, and the code check finds the User again from it: if the User disconnected that provider meanwhile, or the account now signs in as someone else, it ends with `sign_in_expired`. A password change doesn't end a provider's pending sign-in (no password was checked); it ends a password one. The outcomes above (`email_unverified`, `disconnected`, `cancelled`, `failed`) come first and are unchanged. Connecting a provider from the Security page (a ticket, below) is not a sign-in and never asks for the code.

In the web app, **Google** and **GitHub** (named "Continue with Google" / "Continue with GitHub" for screen readers) are plain links side by side above the email and password form on `/login` and `/register`, with an "or" divider between them and the form. They show only for the providers `GET /api/auth/providers` lists: an invisible placeholder holds their place until the answer arrives, and nothing shows when none are enabled or the call fails, because the form still works (full page loads to `GET /api/auth/oauth2/<provider>`, with the page's `returnTo` when it passes `safeReturnPath`). On success the browser lands on `/auth/callback`, which waits for the app's load-time refresh to turn the cookie into an access token and then goes to `returnTo` (checked with `safeReturnPath` again) or `/`. If the cookie is not accepted it goes to `/login?error=failed`, keeping `returnTo`. On failure `/login` shows a message for the `error` code, naming the `provider` (an unknown provider is not echoed).

On the Security page (`/settings/security`) a **Connected accounts** card sits under the sessions card (designs 32a/32b). It has a row for each provider `GET /api/auth/providers` lists, Google first, plus any provider the User has connected that has since been switched off, and is hidden when there are none. A connected row reads "Connected as <account name>" ("Connected" when the name is null), any other "Not connected". It loads on its own, so a failure shows "Couldn't load your connected accounts." with Try again and leaves the sessions above it alone; if the providers can't be asked, the connected ones still show. A connected row has a **Disconnect** button. It opens "Disconnect Google?" (32g, "You won't be able to sign in with Google. You can connect it again any time."); Cancel changes nothing, confirming sends the `DELETE`, reloads the list and shows a notification. When the User has no password (`hasPassword` false) and only one provider is connected, the button opens "Set a password first" (32h) instead, whose "Set a password" goes to `/settings/profile?password`, which opens the password window; a `409 last_sign_in_method` from the server opens the same dialog. A row that is not connected has a **Connect** button: it asks for a ticket (`useMutation`) and then does a full page load to `/api/auth/oauth2/<provider>?link=<ticket>`. On `reauth_required` it opens "Sign in again to connect Google", whose "Sign in again" signs out and goes to `/login?returnTo=/settings/security`. On load the card reads `connected`, or `error` with `provider`, from the address: it shows a notification ("Connected Google.") or the message for the error (a generic one for a code it doesn't know, and an unknown provider is never echoed), reloads the list and removes the parameters from the address.

### Connecting

Connecting a provider goes through a ticket, because the OAuth start is a full page load that carries no Bearer token. `POST /api/users/me/linked-identities/{provider}/link-ticket` checks that the Session started within `nimbus.auth.link-recent-sign-in` (default 10 minutes; a stolen access token alone must not be able to attach someone else's account, and a password check wouldn't work for Users who have none), then returns a random opaque ticket. A ticket lasts 2 minutes, works once and is bound to the Session that asked for it, to the provider it was asked for, and to the browser that asked: the answer sets an `HttpOnly`, `Secure`, `SameSite=Lax` cookie `link_binder` (path `/api/auth/oauth2`, 2 minutes) holding a second random value, which must come back on the callback. Without it anyone could send a victim a link carrying their own ticket and get the victim's Google account connected to their Nimbus account (login CSRF). A ticket that is used with the wrong provider or without its cookie is burned and gives `expired`. It is kept in memory (`LinkTickets`), so a restart only makes the User press Connect again.

`GET /api/auth/oauth2/{provider}?link=<ticket>` keeps the ticket only in the handshake's HTTP session, like `returnTo`; it is never sent to the provider. On the callback, a handshake with a ticket does not sign anyone in: no Session is started and no refresh cookie is set. The ticket is redeemed (unknown, expired, used, for another provider, without its cookie, or its Session has ended: `expired`), then the profile is read with the same rules as sign-in (`email_unverified` still applies) and, under a lock on the User's row, which is also where the Session is checked once more, so a "sign out everywhere" can't be overtaken by a connect:

- already linked to this User: success, and `account_name` is refreshed (no email);
- linked to another User: `already_linked`; the User already has another account of the same provider: `already_connected`; nothing changes either way;
- otherwise it is linked to the ticket's User with its `account_name`, and the provider's `disconnected_providers` mark is deleted. The provider account's email may differ from the User's. The User's email, verification state, password and Sessions don't change, and no domain event is published.

Success redirects to `PUBLIC_URL/settings/security?connected=<provider>`; failure to `/settings/security?error=<code>&provider=<provider>` with `already_linked`, `already_connected`, `email_unverified`, `cancelled`, `failed` or `expired`. After a new link the User gets an email through `Mailer`, "Google was connected to your Nimbus account", with the time (UTC) and a button to the Security page, in the same "Ink header band" layout as the code emails (`MailFrame`); a failed send is logged.

### Disconnecting

Disconnecting deletes the Linked identity and writes the User's `disconnected_providers` mark for the provider (updating `disconnected_at` if it exists), in one transaction under a lock on the User's row, which is also where the "last way to sign in" check runs, so two disconnects at once can't both pass. The mark makes rule 3 refuse the provider on the User's email (see above); the same provider account is free to sign in as another User, or to create one (rules 1 and 4). Sessions stay signed in. After the commit the User gets an email through `Mailer`, "Google was disconnected from your Nimbus account", with the time (UTC) and a button to the Security page, in the same "Ink header band" layout as the code emails (`MailFrame`); a failed send is logged and doesn't undo the disconnect. `/login` shows "You disconnected Google from your Nimbus account. Sign in another way, then connect it again from Security." for `disconnected`.

## Email verification

Registering with a password creates an Unverified User, signs them in, and, after the transaction has committed, emails them a **Verification code** through the `mail` module ([mail.md](mail.md)). A failed send is logged and never fails the registration.

- The email follows the "Ink header band" design: HTML with a plain-text alternative, the code in large type, and "Enter this in Nimbus to verify your email. It expires in 15 minutes." The code is kept out of the subject, the title and the hidden preview line. The header logo comes from `MAIL_ASSETS_URL` (see [mail.md](mail.md)). `mail` owns the shared `MailFrame` and `NoticeMail` layouts; identity supplies the code card, message wording and plain-text alternatives for verification, reset, provider and email-changed emails.
- The code is 6 random digits, valid for 15 minutes. A User has at most one live code: a new one replaces the old.
- 5 wrong tries cancel the code (it is deleted). Wrong tries are counted under a lock on the code's row, so parallel guesses can't race past the limit, and the count is committed even though the request fails.
- Only a keyed hash is stored: HMAC-SHA256 over `<user id>:<code>`, with a key derived from `JWT_SECRET` (so rotating `JWT_SECRET` also cancels live codes). Codes are compared in constant time. The code never goes into an event: events are stored, so it would sit in the database in plain text.
- Registering an email that already exists is `409`, verified or not. Nobody can take over an Unverified User. A squatted address is recovered by signing in with Google or GitHub on it (see Linked identities) or, for any email, by resetting the password with a Reset code, which verifies the email (see Forgot password).
- Users who were unverified before this existed stay unverified and meet the gate. No code was ever issued for them, so they ask for one with Resend.
- **Send limits.** Emails to one address are spaced at least 60 seconds apart and capped at 5 an hour, counted per email address (lower-cased) in memory with the same sliding-window limiter as the other limits. The send at registration counts. A registration over the limit still gets a code, but it is not emailed; the gate's countdown tells the User when Resend works. The budget (`EmailSendBudget`) is not specific to Verification codes: Reset codes spend the same one, and so do email change codes, counted for the new address. A refused send spends nothing.
- Unverified Users are never deleted automatically.

## Changing the email

A verified User changes their email from Profile. A **Verification code** goes to the new address, and the email changes only once it is entered there, so a typo can't lock them out and the old email keeps working until then.

- **Request** (`POST /api/users/me/email-change`). The email is trimmed, lower-cased and checked with the email rule. In order: the Session must have started, or the User must have confirmed it was them in it (Confirm it's you, below), within `nimbus.auth.link-recent-sign-in` (default 10 minutes; `reauth_required` otherwise, because a stolen access token alone must not move the account to another inbox); the address must not be the User's own (`same_email`) nor another User's (`email_taken`, which reveals nothing registration doesn't); and the send budget of the **new** address is spent (`429` otherwise, nothing issued). Then, under a lock on the User's row, a code is issued with the new address beside it and mailed after the commit; a failed send is logged.
- The code follows the same rules as the other emailed codes (`EmailedCodes`, kind `EMAIL_CHANGE`, with a key of its own): 6 random digits, valid for 15 minutes, 5 wrong tries cancel it, only an HMAC-SHA256 stored, never in an event. One pending change per User: asking again, for the same address (Resend) or another, replaces it and its code. A pending change doesn't hold the address. There is no way to read or cancel a pending change; one the User walks away from expires.
- The email ("Confirm your new Nimbus email") uses the Verification code layout with the heading "Confirm your new email", "Enter this in Nimbus to change your email to this address. It expires in 15 minutes." and "If you didn't ask to change your Nimbus email, you can ignore this email." The code stays out of the subject, title and preview line.
- **Confirm** (`POST /api/users/me/email-change/confirm`). Under a lock on the User's row and the code's row: a right code sets the email to the pending address (it stays verified), uses the code up, and cancels any Reset code or Verification code the User has: those were mailed to the old address, and a Reset code there would let whoever reads the old inbox set the password. When another User has the address by then, the transaction rolls back and the answer is `email_taken`, so the code is not used up; the unique constraint on `users.email`, flushed in the same transaction, settles a race. The recent sign-in is not checked again: the code from the new inbox is proof enough, and finding it may take a while. `EmailChanged` is published in the same transaction.
- **The old address is told** after the commit, in the `NoticeMail` layout without a button (design 39l): "Your Nimbus email was changed" (subject and heading), "The email on your account is now n•••@gmail.com. This address won't get Nimbus emails any more.", the details "New email" and "When" (`d MMM yyyy, HH:mm UTC`, as the other notices: Nimbus stores no time zone), the tile "If you made this change, there's nothing to do. If you didn't, contact your Nimbus admin straight away." and the footer "This notice is sent to your previous address and can't be turned off." The new address shows only its first character, `•••`, `@` and the whole domain. There is no undo link: whoever reads the old inbox may not be the User any more. A failed send is logged and the change stays. Notifications may later take this notice over (#131).
- **Only the email changes.** Sessions, refresh tokens, remembered browsers, the password, Two-step verification, Linked identities and `disconnected_providers` stay as they are. Linked identities keep signing in by provider account (rule 1); a later sign-in with an unlinked provider account on the new address links by email (rule 3), as for any verified User. Failed sign-ins counted against the old address are left behind. Audit log entries keep the email they were written with.
- **Confirm it's you** (`POST /api/users/me/confirm {password, twoStepCode | recoveryCode}`, `204`). A sign-in too old for the request above is renewed without signing out: the password, checked outside any transaction and counted per User with the same count as wrong current passwords when changing it (`400` with `errors.password`; `429` with `Retry-After` over it), then, for a User with Two-step verification, a Sign-in code (drift, no reuse) or an unused Recovery code, under a lock on the User's row (`400 two_step_required` without one, `400 invalid_two_step_code` for a wrong one, counting toward the hourly code lock; a used Recovery code publishes `RecoveryCodeUsed`). The password is checked first, so a wrong one never tells whether the User has Two-step verification. A right answer stamps the session's `confirmed_at`, which the request above counts like a sign-in for 10 minutes. A User without a password gets `409 no_password` and signs in again. Needs a running session (`401`); Unverified Users get the usual `403`. Only the email change counts it: connecting a provider and setting up Two-step verification still need a recent sign-in.
- **In the web app**, Profile (`/settings/profile`, design 39a) has one card with a row each for Display name (**Edit** opens a window with the rename form), Email (with a "Verified" pill and **Change email**) and Password ("Last changed 3 months ago" from `passwordChangedAt`, left out when it is null; **Change password**, or **Set a password** for a User without one, opens a window: designs 39m–39o; changing still signs the other devices out, and the row then says "Last changed just now"). The Password page is gone: `/settings/password`, and "Set a password first" on the Security page, lead to `/settings/profile?password`, which opens the password window. Change email opens a window with the stepper "Confirm it's you · New email · Enter code" (39d–39k): the current email as text and a "New email" field, then "Check your new inbox" with six code boxes, "Resend code in 0:42" (60 seconds, or the server's `Retry-After`) and "Use a different email". A wrong code shows "That code didn't match. 3 tries left."; `code_expired` shows "This code has expired" with Send a new code; `email_taken` at confirm goes back to the address. `reauth_required` shows step 1, Confirm it's you (39b, 39c): "You signed in a while ago. Enter your password to keep going.", then for a User with Two-step verification "Enter your Sign-in code" with "Use a recovery code" and Back (which keeps the password). Back on the password returns to the new address, still typed. The window stays open while an answer is checked. A right answer sends the code to the address typed before. A User without a password, or a `no_password` answer, gets the sign-in-again window instead, which brings them back to Profile. The design's "Forgot password?" on step 1 is left out: the forgot-password page sends a signed-in User home. On success the window closes, the User shown everywhere is the one the server returned, and a toast reads "Email changed to ...".

## Profile picture

The image shown for a User next to their name (see `GLOSSARY.md`). `avatarUrl`, wherever it is returned (the User, `UserSummary`, and through it the Audit log actor and role holders), is worked out when it is read:

- **Never chosen** (`picture_source` null, every User until they upload): `avatar_url`, the picture the last Google or GitHub sign-in brought, or null. As before Users could choose.
- **Uploaded**: the uploaded photo's address, `nimbus.profile-pictures.base-url` (`PROFILE_PICTURES_URL`, default `/api/profile-pictures`) plus `/` and its key. The setting lets a public bucket on our own domain serve the photos later without code changes (ADR 0006).
- **Initials** (`picture_source` `initials`): `avatarUrl` is null. Removing the shown uploaded photo chooses it.
- Google and GitHub are allowed by the table but not chosen yet.

Uploading (`PUT /api/users/me/profile-picture`) checks the size, then the file's first bytes (JPEG, PNG or WebP; WebP is read with TwelveMonkeys `imageio-webp`), decodes it, takes the centred square, scales it to 256x256 with transparency laid on white, and writes a new JPEG (quality 0.85) with ImageIO, which keeps none of the original's metadata (EXIF, location). The web app crops in the browser first, so the square is usually the whole image.

Uploads are limited to 10 per User in a sliding hour (`ProfilePictures`, in memory like the other limiters, so per API instance). The controller refuses a User over the limit before reading the file; the upload is counted before it is decoded and stays counted when the file is refused (`400`), since decoding costs. It is given back only when the bucket or database fails. Removing is not limited.

Removing (`DELETE /api/users/me/profile-picture`) clears the key and upload time under the User's row lock, and chooses Initials when the uploaded photo was the one shown (any other choice stays), then deletes the object; a failed delete is logged like the one after a replace. Without an upload nothing is written.

Order: the JPEG is stored in the bucket under `profile-pictures/<key>`, where the key is 16 random bytes in URL-safe base64 (22 characters, new on every upload); then, under the User's row lock, the key and upload time are saved and the choice becomes Uploaded; then the photo it replaced, if any, is deleted. If saving the User fails, the new object is deleted, best effort. Failed deletes are logged at WARN and the object stays in the bucket unused; there is no clean-up job. Objects go through the `storage` module ([storage.md](storage.md)).

The endpoint checks the 5 MB itself. The global multipart ceiling (`spring.servlet.multipart.*`, 10 MB) is for every upload endpoint; a file over it is refused with the same `file_too_large` here (multipart is resolved lazily, so that refusal reaches the identity error handler). Tomcat swallows up to 16 MB left unread after a refusal (`server.tomcat.max-swallow-size`), so a client sending a larger file by mistake still reads the answer; past that it sees the connection close. Large images are decoded at about 4 megapixels at most (ImageIO subsampling), so parallel uploads stay small in memory. If the bucket can't be reached, uploads and picture loads answer `503`.

## Forgot password

A User who forgot their password asks for a **Reset code** by email and enters it with a new password. Reading the email proves they own the address, so a right code also verifies it. Nothing in the flow says whether an email is registered.

- **Request** (`POST /api/auth/password-reset`) answers `204` for every email. Before answering it checks the per-IP limit and spends the shared send budget (below) for the address typed, whether or not a User has it, so a `429` with `Retry-After` looks the same either way and nothing is issued or sent then (a live code is unchanged). The lookup of the email, issuing the code and the send run after the response, on the service's own small bounded pool (full: the request is dropped and logged), so the answer and its timing are the same for every email. An unknown email does nothing. Users with no password (Google or GitHub only) get a code like anyone else. Any failure is logged and never reaches the caller.
- The Reset code follows the same rules as the Verification code: 6 random digits, valid for 15 minutes, at most one live code per User (a new request replaces the old code), 5 wrong tries cancel it, wrong tries counted under a lock on the code's row, only an HMAC-SHA256 over `<user id>:<code>` stored (with a key of its own, also derived from `JWT_SECRET`), compared in constant time, never in an event. Both kinds share one table, `emailed_codes`, with one row per User and kind, so a pending Verification code and a pending Reset code never replace each other. In the code, one class (`EmailedCodes`) holds the shared rules for issuing, checking and counting tries.
- The email is rendered by identity in the same "Ink header band" layout as the verification email: heading "Reset your password", "Enter this in Nimbus to reset your password. It expires in 15 minutes.", "Your reset code is" directly above the code, "Nimbus will never ask for this code by phone, chat or email." and "If you didn't ask for this, ignore this email. Your password won't change." Subject "Your Nimbus password reset code"; the code stays out of the subject, title and preview line. Plain-text alternative included. Mailed after the code's transaction commits.
- **Reset** (`POST /api/auth/password-reset/confirm`): the new password is checked against the password rule first (a rule-breaking one costs no try) and hashed outside any transaction, for every request, so an unknown email takes as long as a known one. Then, under a lock on the User's row and the code's row: a right code deletes the code, sets the password, marks the email verified (publishing `EmailVerified` in the same transaction when it wasn't, so a squatter's password stops working and the configured admin who registered with a password becomes Platform admin) and revokes every session of the User. After the commit the failed sign-ins for the email are cleared, so a User locked out by failed guesses can sign in with the new password at once. The User is not signed in. Linked identities and anything in `access` are untouched.
- **Two-step verification** (ADR 0005). A User who has it also needs a Sign-in code (`twoStepCode`) or a Recovery code (`recoveryCode`), so someone with only their inbox can't change the password or end their Sessions. It is asked for only once the Reset code is right, so a wrong or expired Reset code answers as above whatever second code comes, and nothing tells whether a User has it before then. Without a second code the answer is `two_step_required`; a wrong one (or a used Recovery code) is `invalid_two_step_code`, counting toward the hourly lock on code checks (see Two-step verification), not toward the Reset code's tries. Either way the transaction rolls back, so the Reset code is not used up and its tries stay as they were. Every confirm counts toward the per-IP limit, `two_step_required` too. The second code is checked as at sign-in, in the same transaction and under the same row lock as the reset: a right Sign-in code is used up, a right Recovery code is marked used and publishes `RecoveryCodeUsed`. Two-step verification stays on. The web app shows the second code under the new password after `two_step_required` (code boxes, or a Recovery code box with "Use a recovery code"), keeping the Reset code and the password as typed.
- **In the web app**, `/forgot-password` has two steps on one page, with the email kept in memory only (a reload returns to step 1; a signed-in User is sent to `/`). Step 1 asks for the email and calls the request endpoint. Step 2 shows six code boxes and one "New password" field and calls the reset endpoint: a wrong code keeps the boxes filled and red with the tries left; an expired or cancelled code (`code_expired`) swaps the password field for "Send a new code"; a rejected password shows under the field and keeps the code. Resend waits 60 seconds after each send (or the server's `Retry-After`). On success the User goes to `/login` with the email filled in, the password field focused and a toast "Password updated. You were signed out on other devices." `/login` links to the page from the Password label row.
- Known trade-off: access tokens already issued stay valid until they expire (up to 15 minutes), as after any sign-out; they are not denylisted.
- Known gap: a wrong code for a registered email answers `invalid_code`, while an unknown email always answers `code_expired`, so the confirm step can tell the two apart. The request step does not. This is accepted: `POST /api/auth/register` already answers `409` for a registered email.
- **Limits.** The request spends the same per-address send budget as Verification codes (60 seconds apart, 5 an hour, per lower-cased email), so combining flows can't flood an inbox, and it is spent for unregistered emails too. Each endpoint also has a per-IP limit (see Rate limits). Together with the 5 tries per code they bound guessing to about 25 tries an hour per address. Known trade-off: anyone can use up an email's send budget by typing it in the form: one request a minute keeps the hourly cap full (5 emails an hour to the owner) and blocks the owner's own requests and Resend, within the per-IP limit of 10 per 15 minutes per client. In the web app a `429` on step 1 shows "Too many attempts. Try again in m:ss." under the button; on step 2 it shows the rate-limited layout (boxes and button disabled, "Resend paused"), and Resend counts down from `Retry-After`.

## Two-step verification

A User can turn on **Two-step verification** on the Security page, so that signing in also needs a **Sign-in code** from an authenticator app, or one of their **Recovery codes** (ADR 0005). This section covers turning it on and off, signing in, with a password or with Google or GitHub, by a Sign-in code or a Recovery code, remembered browsers, and making new Recovery codes.

- **Codes.** RFC 6238 time-based codes: HMAC-SHA1, 6 digits, 30-second steps, from a 160-bit random key, written in identity with `javax.crypto` (no library). A code for one step before or after now is accepted too, for phone clocks that are a little off. `two_step_authenticators.last_used_step` keeps the newest step whose code was accepted (at setup, the code that proved the key), so the same code never works twice.
- **Setup** is three calls and nothing is stored before the last. Start makes a key and returns it as base32 (`key`, 32 characters, which the web app shows in groups of four) and as `otpauth://totp/Nimbus:<email>?secret=<key>&issuer=Nimbus`, which the web app draws as a QR code in the browser (the key never goes to another server). Verify checks a code from the app against that key and makes the 10 Recovery codes. Turn on stores both. The setup in progress lives in memory, one per User, for 10 minutes (`TwoStepSetups`, like `LinkTickets`). It belongs to the session that started it: another session of the User (say, one whose access token was stolen) can't prove it or turn it on. It allows 5 wrong codes. A restart, a new start, the 5th wrong code or closing the window (`DELETE …/setup`) throws it away, and the app entry scanned for it never works.
- **Recent sign-in.** Starting a setup needs a Session that began within `nimbus.auth.link-recent-sign-in`, as connecting a provider does: otherwise a stolen access token could put Two-step verification on the thief's phone and lock the User out.
- **Recovery codes** are 8 random lowercase letters and digits, shown as `xxxx-xxxx`. They are compared with capitals, whitespace (tabs and no-break spaces too) and dashes (Unicode hyphens and dashes, and the minus sign) ignored, so a code copied from a document still works. Only an HMAC-SHA256 of the normalised code, keyed from `TWO_STEP_SECRET` and bound to the User, is stored, so they can't be shown again. At sign-in (`{recoveryCode}` on `POST /api/auth/two-step`, "Lost your phone? Use a recovery code" on `/login/two-step`) a right one is marked used (`used_at`) under the User's row lock, so it works once, and the Security page's `recoveryCodesLeft` goes down. A wrong or used one counts like a wrong Sign-in code.
- **`TWO_STEP_SECRET`** (in `apps/api/.env`, base64 of at least 32 bytes) gives two keys: one encrypts each authenticator key with AES-GCM (bound to its User, so a row can't be moved to another), one keys the Recovery code hashes. The app refuses to start without a usable value, naming the variable. Everyone using one database must use the same value. Changing it means every User sets Two-step verification up again (decrypting fails with a message saying so).
- **Signing in.** A right password for a User with Two-step verification starts no session. Instead `POST /api/auth/login` answers `{twoStepRequired: true}` and sets `two_step_pending` (`HttpOnly; Secure; SameSite=Strict; Path=/api/auth/two-step; Max-Age=300`), a random single-use id of a pending sign-in held in memory (`PendingSignIns`, like `LinkTickets`; a restart sends the User back to sign in). The pending sign-in lasts 5 minutes and allows 5 wrong codes, and a User holds at most 3 (a new one drops their oldest, so signing in again and again can't fill the memory). It belongs to the password it was started with: once the password is changed or reset, it ends with `sign_in_expired`. (One started by Google or GitHub belongs to that provider instead; see Linked identities.) `POST /api/auth/two-step` with a right code ends it and starts the session. The code check runs under a lock on the User's row, so one code can't start two sessions. Wrong passwords keep their own limits; a refresh never asks for a code. The web app sends the password form to `/login/two-step` (keeping `returnTo`), and `sign_in_expired` back to `/login` with "Your sign-in timed out. Sign in again."
- **The hourly lock.** `nimbus.auth.wrong-sign-in-codes-per-hour` (default 10) wrong codes for one User in a sliding hour, counted across pending sign-ins, setup, View new codes, Remove and forgot password (`SignInCodeLock`), make every code check for that User a `429` with `Retry-After` until the oldest leaves the hour; a User over it is refused before any work (their row is not locked, no key decrypted). Without it, someone with the password could keep guessing by signing in again after every 5 wrong codes. Checks are counted just before the code is compared (failures that are not about the code never count), and a right code takes its own back.
- **Turning it on** publishes `TwoStepEnabled` and ends no Session; the User's other browsers keep working.
- **View new codes** (`POST …/two-step/recovery-codes`) asks for a Sign-in code, not a Recovery code, so a lost list can't make a new one. A right code is used up as at sign-in, the old set is deleted and 10 new codes are shown once (only their hashes are kept), and `RecoveryCodesRegenerated` is published, all under the User's row lock in one transaction. The web app shows them with Copy, Download .txt and "I've saved these codes"; the count on the card goes back to 10 as soon as they are shown.
- **Remove** (`DELETE …/two-step`) asks for a Sign-in code, or a Recovery code for a User who lost their phone ("Use a recovery code" in the window). Under the User's row lock, in one transaction, the code is checked as at sign-in, the authenticator row and every Recovery code are deleted, and `TwoStepDisabled` is published. It ends no Session. From then on password and Google or GitHub sign-ins start a session straight away (a pending sign-in already waiting for a code ends with `sign_in_expired`), and setting it up again makes a new key and new codes. The card goes back to Off.
- **Remembered browsers.** "Don't ask again on this device for 30 days" on both versions of `/login/two-step` sends `rememberBrowser: true` with the code. A right code then also stores a row in `remembered_browsers` (in the same transaction as the Session) and sets `two_step_remembered` (`HttpOnly; Secure; SameSite=Lax; Path=/api; Max-Age=2592000`), a random 256-bit token of which only the SHA-256 is kept (`RememberedBrowsers`). Lax, so the browser sends it on the redirect back from Google or GitHub; `Path=/api`, so "Sign out all other devices" receives it. `POST /api/auth/login` and the Google/GitHub callback skip the code when the cookie matches an unexpired row of that User; another User on the same browser is asked as usual. It lasts a fixed 30 days from when it was ticked: using the browser doesn't extend it. Signing out keeps it. A password change, a reset and Remove delete all of the User's rows; `sign-out-others` deletes all but the row of the cookie sent with it (all of them without one). The hourly session cleanup deletes expired rows.
- **Turning it off by hand.** A User who has lost both their phone and every Recovery code can't turn it off themselves (ADR 0005); the team does it in the database:

  ```sql
  DELETE FROM two_step_authenticators WHERE user_id = '<user id>';
  DELETE FROM recovery_codes WHERE user_id = '<user id>';
  DELETE FROM remembered_browsers WHERE user_id = '<user id>';
  ```

## Rules

- Email and display name have surrounding whitespace removed before validation. A valid email is not blank, passes Jakarta Validation's `@Email` and is at most 254 characters (`@ValidEmail`); `@ValidPassword` is the password rule below. Registration, changing a password and the admin seed all use these two constraints.
- Email is unique and stored lower-cased. The unique constraint, not the up-front check, guarantees one User per email when registrations race.
- Password: 8–128 characters, no composition rules, kept exactly as typed. Hashed with Argon2id (stored with an `{argon2}` prefix so the algorithm can change later), outside any database transaction because it is slow. Not bcrypt, because bcrypt only uses the first 72 bytes.
- Setting or changing a password follows the same rules. The current password is checked and the new one hashed outside any transaction; wrong current passwords are counted per User (`nimbus.auth.failed-sign-ins-per-email`, same window), and a correct one takes its attempt back. This count is separate from failed sign-ins on purpose: sharing it would let anyone who knows an email block a signed-in User from changing their password. A stolen access token therefore gets that many guesses here as well. The update runs under a lock on the User's row, so it cannot interleave with a provider sign-in that removes the password.
- Display name: one rule (`DisplayName`, a function that removes what is not allowed; a name is valid when nothing would be removed) for registration, renaming and names from a provider. After surrounding whitespace is removed (no-break and other Unicode spaces included) it needs at least one visible character (not only spaces, marks or invisible characters) and at most 100 characters, counted as code points so an emoji is one. It must not contain control characters (ASCII or C1), line or paragraph separators, lone surrogates, private-use characters, the combining grapheme joiner, or Unicode _format_ characters: zero-width space, word joiner, byte order mark, soft hyphen, and every bidirectional mark, embedding, override and isolate, which could hide or reorder the text around a name. Exceptions that real names need: U+200D (zero-width joiner) and U+200C (non-joiner) **between two visible characters** (emoji sequences, Persian and Indic scripts); _tag characters_ only in a flag sequence (a black flag, 2 to 7 tag letters or digits, the cancel tag, as in the flag of England), because elsewhere they carry text nobody can see; _variation selectors_ only U+FE0E or U+FE0F after a character that is not a letter (emoji, keycaps) and the ideographic ones after a Han character, never two in a row; and combining marks only on a visible character, at most 5 stacked. Typed names that break the rule get `400` with `errors.displayName` saying which part. A provider's name is cut at the last whole character (as people see it, so never between an emoji and its skin tone or inside a flag) at or before 100. Known gaps: look-alike letters from other scripts and a few invisible _letters_ (e.g. Hangul filler U+3164) are not caught; code points the JDK's Unicode tables do not know yet are allowed, so the newest emoji work, and a format character added in a later Unicode version gets through until the JDK is updated; names stored before this rule are not rewritten, so the rename form can open with a name it would now refuse.

## Rate limits

Counted in memory over a sliding 15-minute window (`nimbus.auth.limit-window`; the two email limits and the Sign-in code lock use their own 60-second and 1-hour windows), which is enough while the API runs as one instance. Over a limit, the endpoint answers `429` with `Retry-After` in seconds.

| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------- |
| Failed sign-ins per email. Further attempts, even with the right password, get `429` until the oldest failure leaves the window. A successful sign-in doesn't count, but doesn't erase earlier failures either. Known trade-off: anyone who knows an email can keep it locked out (spec #1, Q19). | 5       | `nimbus.auth.failed-sign-ins-per-email`           |
| Failed sign-ins per IP address, across all emails (stops one client spraying guesses over many emails)                                                                                                                                                                                            | 20      | `nimbus.auth.sign-ins-per-address`                |
